# 03 — 归因器与编排 CLI（面试复习版）

> 覆盖：失败归因器（13 条签名规则层 + 弱模型 LLM 层 + 报告层）与子进程编排 CLI（record / generate / run / analyze）。出处细节见 dev_docs 下 attributor/ 与 cli/ 两模块的 plan、spec、review、test-report，以及实验报告、终审分析、STATUS。

## 1. 这一页讲什么 + 本档案复习法

**这一页讲什么（3 句）**

失败归因器把一次 Hercules 失败运行变成"可信归类 + 可回查证据引用"：13 条错误串签名规则层命中即定类（零模型、确定性），只有模糊区（断言不匹配、无签名长尾）才交给弱模型 LLM 层，而 LLM 的每条引用都被程序回查——查无此证强制降级"无法定位（inconclusive）"且置信度压 0.30。子进程编排 CLI 用 record / generate / run / analyze 四条命令把录制→蒸馏→执行→归因串成一条链：run 走独立项目根的 Hercules 子进程（key 只经环境变量注入、日志强制脱敏、--dry-run 没 key 也能干跑）——这条子进程路线第一天就定死，因为进程内有四个实证的坑（StaticLTM 串场、config 单例、时间戳目录混叠、PlaywrightManager 关闭竞态），且上游自己的 MCP server 也用子进程。真实验证做了两条：F5/M4（评测六十格里唯一失败的一格，按钮文案改写）经"S10 签名 + 无 LLM 降级"产出证据直指文案改写的报告；F1 真实链路（record→generate→run passed 62 秒 / 7.3 万 token→analyze）全链路验收通过；--polish / --llm 两个 flag 真机未验收，属如实标注的待验收项。

**本档案复习法**

第一遍背熟第 2 节 60 秒主线，能脱稿一口气说完；第二遍过第 3 节 16 张决策卡——先遮住答案自测，每张目标 30-60 秒说出口；第三遍把第 4 节坑卡当故事讲（固定"现象→修复→教训"三段式，10 张卡覆盖全部 13 个坑）；考前 10 分钟只扫第 5 节必背数字；最后按第 6 节联动回 qa-bank 对应大题。

## 2. 60 秒主线

被问"归因器怎么设计的"，一段说出口：

"归因器是三层防线。第一层规则层：引擎的错误串是源码固定文本，13 条签名命中即定类——零模型、确定性、可单测，'规则层零模型依赖'是结论，也是有测试钉死的属性。第二层只处理模糊区：断言不匹配、无签名长尾这类'产品 bug、用例过时还是 agent 点错'分不清的场景，路由给弱模型，但 LLM 拿到的是编号证据包，输出的每条引用都被程序回查——引用号要存在、定位符要能解析、摘录必须是原文子串；查无此证强制降级'无法定位'，置信度压 0.30。第三层报告层：每条结论都带可回查的证据引用和替代假设，inconclusive 也保留种子证据。编排侧是四条命令的 CLI：record 录事件流、generate 蒸 Gherkin、run 真实执行、analyze 出归因报告。run 走独立项目根的子进程，第一天就定死——因为进程内有四个实证的坑：StaticLTM 单例串场、config 单例重置丢内存态、import 时时间戳目录混叠、PlaywrightManager 关闭竞态；而且上游自己的 MCP server 也用子进程，我照抄了这个成熟先例。key 全链安全：只经环境变量注入、命令行永远干净、所有外部文本进日志前一律脱敏。"

**四命令速览**（细节进决策卡与坑卡）

| 命令 | 干什么 | 关键行为 | 退出码 |
|---|---|---|---|
| record | 录制浏览器操作 → 事件 JSON | 有头 chromium 起页 → 注入录制器 JS（确认 R2GRecorder 挂载成功）→ 0.2 秒轮询停止条件（谓词 / Ctrl+C / 限时，默认不限时）；页面被关或录制器丢失＝跨文档导航 → exit 2 不落盘；只录到初始导航一条事件（事件数 ≤1）→ 记告警照常保存；--manual 走书签脚本不启浏览器，--out 默认带时间戳的 recordings 目录 | 成功 0；启动/跳转/注入/页面丢失/URL 不可达 2；第二次 Ctrl+C 强制中止 130 |
| generate | 事件 → Gherkin feature | 默认纯模板零模型；--polish 才润色（失败回退骨架、照常 exit 0）；两段式蒸馏 + --test-data 填占位符密码（缺值保留占位符逐键警告、多余键警告；值形态错 exit 2；骨架自检失败是 bug 级另计）；--out 默认与事件同目录同名 .feature | 成功 0（含占位符保留、润色回退）；输入错 2；骨架自检失败 1 |
| run | 真实执行 feature | 独立项目根（--out-dir 下自建 opt 根，run_id 带时间戳与用例名、冲突追加序号）的 Hercules 子进程；key 只经 env、日志脱敏、默认超时 900 秒超时杀整组；摘要含状态/耗时/token/成本（取不到打 -）+ JUnit + 同名 HTML + 证据目录 + 失败消息（截 500 且 CLI 侧二次脱敏）+ 末行 analyze 提示 | passed / dry-run 0；用例失败 1；子进程超时 3；JUnit 缺失/不可读 4；输入错（feature/key 缺失等）2；Ctrl+C 130（提示子进程可能残留） |
| analyze | 运行目录 → 归因报告 | 默认纯规则、逐字节确定；--llm 才开模型（构造失败自动降级纯规则）；JUnit 默认自动发现最新一份，也可 --junit 指定；每个失败用例出 json+md 一对（默认写在运行目录的 analysis 下）+ 摘要表；全过不建目录 | 出报告 0（哪怕用例失败）；运行目录不存在 2；JUnit 缺失/不可解析 3 |

**工程小事两条备着**：入口是 `uv run python -m record2gherkin <子命令>`——不动上游锁定的 pyproject/uv.lock、不加 console-script（避免越出二开边界）；全部输出走 logger（main 第一步装配 INFO），禁 print——裸 import 时 logger 没有 handler，不装配用户什么也看不到。无子命令 → argparse 退 2；未捕获意外异常 → 最外层兜底 error 日志（带类型名）退 2，不裸 traceback。

## 3. 决策速答卡（16 张）

### 卡 1｜三层防线：规则层定类、LLM 只碰模糊区、程序回查兜底
- **怎么问**："归因流水线怎么设计的？为什么还要 LLM？"
- **30-60 秒答**："引擎错误串是源码固定文本，13 条签名命中即准——确定性、可单测；规则层零模型依赖：证据、规则、报告三文件不 import 任何 LLM/网络模块，这条属性有专门测试钉死，不是口头承诺。LLM 只在 product_bug（产品缺陷）、test_rot（用例过时）、agent 点错分不清的模糊区发言，做模糊区摘要、不做定类初审。全 LLM 归因被否——不确定、贵、会幻觉；全规则也被否——断言 EXPECTED/ACTUAL 不匹配的根因多样，规则定不了 product_bug。"
- **追问预案**："数据流是什么？"——证据加载（JUnit 缺失/不可解析是唯一加载期抛错，其余缺件记警告容错）→ 签名匹配 → 确定性签名直接出结果、路由签名或无命中转 needs_llm（转交弱模型的内部路由标记）→ LLM 层 → 报告。"needs_llm 会出现在最终结果里吗？"——不会。"报告长什么样？"——JSON 固定 12 键 + 中文 Markdown（摘录保持原文）；每类一条的中文建议模板共 5 条，确定性拼装。

### 卡 2｜五档分类：从三分类扩出来的两档
- **怎么问**："分类为什么是五档？和总计划三分类什么关系？"
- **30-60 秒答**："product_bug＝页面实际行为与用例预期不符——页面没坏、用例没过时，规则层从不下这个结论，只有 LLM 层敢下；test_rot＝用例依据的元素/URL/文案与当前站点脱节；environment＝站点不可达、浏览器、代理等运行环境问题；agent_limit＝轮次耗尽、超时、坏 JSON 空转、context 超限这类引擎硬上限；inconclusive＝证据不足的诚实输出。agent_limit 从 environment 分出来，因为混着会误导排查方向；inconclusive 给'宁可疑而不定'一等公民出口，避免 LLM 被迫瞎猜。三分类是总计划原文，任务指派即修订，plan/spec 以五档为准。"

### 卡 3｜宁可疑而不定：inconclusive 是被鼓励的合法答案
- **怎么问**："LLM 的输出你怎么约束？"
- **30-60 秒答**："SYSTEM_PROMPT 硬约束逐条：引用只许填请求里给过的编号，禁止编造文件名、轮次；原话是 'Prefer inconclusive over guessing. inconclusive is a legal and encouraged answer.'（宁可疑而不定，不许猜）；非 inconclusive 必须至少 1 条文本类证据，仅截图文件名不行——本层不读像素；EXPECTED/ACTUAL 形态要并列权衡产品 bug、用例过时、agent 点错三假设；只输出严格 JSON、无围栏无解释。角色限定为只归类与引用、不修 bug；五类判定标准各写一句；温度 0。这样 LLM 最坏行为的下限是诚实的 inconclusive。"

### 卡 4｜查无此证强制降级：回查三规则 + 四条降级路
- **怎么问**："LLM 真的不会瞎编吗？"
- **30-60 秒答**："每条引用程序回查，三条规则：一，引用号必须在证据包里，不存在即丢；二，定位符要能重新解析——thoughts 轮次要界内、feature 行号 1-based 界内、JUnit 失败原文/最终回复/属性值要取得到，解析失败即丢；三，归一化后（连续空白折叠加去首尾）摘录必须是所指原文的子串，不成立即丢。截图类例外：文件存在即通过。结论级再卡一条：非 inconclusive 至少要 1 条存活的文本类引用。四条降级路全部出口 inconclusive、置信度压 0.30：没配 analyzer 或其抛错；调用异常两次；输出非法两次；回查后存活引用不足（此时置信度取原值与 0.30 的较小者，并附被丢引用清单、最多列 5 个）。降级产物标记 decided_by=degraded、保留规则层种子证据与替代假设——inconclusive 也有可查证据。部分引用被丢但存活够用仍采纳，附警告。"
- **追问预案**："证据包怎么组？超限丢什么？"——种子（规则命中全部证据 + JUnit 失败原文 + 最终回复）永不被上限丢弃；上下文取规则命中轮加末 6 轮、每轮摘录纯截断 400 字符；截图按文件名独立成条、末状态对标 [FINAL]；总上限 30 条，超限先丢上下文轮（旧→新）再丢非末状态截图。user 消息另附场景名、失败消息、最终回复、feature 摘录各截 2000 字符，加截图文件名时间序清单（上限 20）。"输出解析怎么做？"——剥 JSON 围栏取首尾大括号解析；五键齐全、类别属五档、置信度夹到 0.05-0.95 再四舍五入 2 位、摘要非空截 2000；首次失败把违反项以机器文本回喂重试一次；LLM 调用异常计一次尝试、不重试解析。"摘录为什么必须纯截断？"——回查要求摘录是原文子串，追加装饰文本会系统性误杀合法引用（坑卡 4 的教训）。

### 卡 5｜证据入口：JUnit XML properties
- **怎么问**："证据从哪来？"
- **30-60 秒答**："上游 JUnit 报告已把 feature、planner 思考、截图等路径写进每个 testcase 的属性里，归因器直接拿它当证据入口，不自己拼目录——自己拼要重复上游逻辑且脆弱。上游有个拼错的键（netwrok），按前缀匹配兼容掉。加载期唯一抛错是 JUnit 缺失或不可解析，其余缺件只记警告容错。"

### 卡 6｜截图↔轮次只做近似对齐
- **怎么问**："截图和 planner 轮次怎么对上的？"
- **30-60 秒答**："文件名带时间戳形态可解析 + 时间序排序 + 末状态对 + thoughts 字面提及建锚，v1 就到这——总计划明确近似即可，step 精确对齐是低收益边界问题、明确 Out of Scope。锚只认字面提及、无锚不造锚；报告明示'近似对齐非逐轮映射'。"

### 卡 7｜置信度分层：低置信必须摆出替代假设
- **怎么问**："置信度 0.95、0.30 这些数怎么定的？"
- **30-60 秒答**："按签名文本与根因的确定性分层：固定引擎串 0.90-0.95；浏览器/工具类 0.75-0.85；语义歧义的元素找不到、404 封顶 0.65-0.75 且必附替代假设——'元素找不到 ≠ 必然用例过时'，产品 bug 也表现为找不到元素。conf<0.8 强制附替代假设，把别的可能摆上台面；单一置信度被否，因为掩盖歧义。一切降级 0.30。"

### 卡 8｜S3 复合签名：轮次耗尽是表象不是根因
- **怎么问**："S3 为什么搞复合签名？"
- **30-60 秒答**："最大失败形态是导航轮次耗尽，但那只是表象。主复合命中后对 thoughts 二跳复扫：见'元素找不到'→ test_rot 0.75；见网络错 → environment 0.75；都没有 → agent_limit 0.90，并附替代假设'轮次耗尽可能因引擎定位能力不足，而非用例过时'。只出 agent_limit 会丢掉最有价值的一跳归因；三个分支各有测试钉住。"

### 卡 9｜analyze 默认纯规则；真实验证两条与 --llm 如实状态
- **怎么问**："analyze 怎么用？真实验证做了吗？LLM 归因生产可用吗？"
- **30-60 秒答**："analyze 默认 analyzer=None——纯规则、离线、逐字节确定，演示链路不隐性依赖 LLM 配置；--llm 才启用，且构造失败自动降级纯规则、照常出报告 exit 0。模型是懒构建：构造 analyzer 不触网不读配置，缺 attributor_analyze 模型档的错误到首次归因才抛，按'analyzer 不可用'降级。真实验证两条：F5/M4 是六十格里唯一失败格（按钮文案从'去下单'改成'马上下单'），失败运行喂给归因器——S10 签名命中路由、无 LLM 降级，报告 inconclusive、decided_by=degraded，种子证据保留且直指文案改写（Missing: '去下单' (found '马上下单')），替代假设含'用例过时'。注意精确语义：S10 是路由签名，无 LLM 下不定类为 test_rot，而是诚实降级 inconclusive；报告的'正确'体现在证据与替代假设把根因摆给了人。F1 全链路：record→generate→run 真实执行 passed（62 秒 / 7.3 万 token，用的是引擎自身 LLM deepseek-v4-pro 全角色，与那两个 flag 无关）→analyze。"
- **追问预案**："那 --llm 生产可用吗？"——如实：--polish / --llm 真机未验收。离线测试只覆盖注入 fake 与降级路径；真实润色取决于 distiller_polish 模型档、真实 LLM 归因取决于 attributor_analyze 档位。原因：离线测试纪律禁止在测试里触发真实 LLM 调用，真机验收依赖 key 与模型档配置；且两者失败都有契约内出口（--polish 失败回退骨架 exit 0 并记 polish_error；--llm 构造失败降级纯规则 exit 0）。话术：'润色与 LLM 归因有完整的降级与回查测试，真实 LLM 归因验收只做了规则层，LLM 层标为待验收'——绝不说"生产可用"，演示也不开这两个 flag。

### 卡 10｜run 包装 runner，不重写执行器
- **怎么问**："执行为什么要包一层 runner？"
- **30-60 秒答**："runner 已解决 key 文件读取、环境变量注入、进程组超时击杀、stdout 脱敏、JUnit 两级定位，CLI 只做编排。绕过 runner 自建子进程被否——复制密钥与进程管理逻辑，双倍泄露面。"

### 卡 11｜两段式蒸馏 + test-data 值契约
- **怎么问**："占位符密码怎么落地的？"
- **30-60 秒答**："占位符形如 {{TEST_DATA:password_序号}}，但引擎侧没有机械消费者（早期分析 P0-2 实证过），填充必须在 generate 期完成。所以两段式：先骨架预蒸馏——纯函数零成本，扫出全部占位符键（保序去重）；再终稿蒸馏只传'需要且提供了'的交集——不烧双份 LLM 调用。缺值保留占位符并逐键 missing 警告，多余键 unused 警告，最后打 output/needed/filled 等摘要。值契约与蒸馏器逐字对齐：bool/null/空白视为未提供，对象/数组直接 exit 2 列坏键——评审抓过'宽收 bool 会摘要虚报 filled 但产物仍留占位符'，缺值警告闭环就断了。"

### 卡 12｜dry-run：没 key 也能干跑
- **怎么问**："dry-run 为什么不需要 key？"
- **30-60 秒答**："dry-run 不执行，只构建运行计划并打印：一行命令（命令行参数里没有 key）+ 经脱敏的环境变量——只列五个键：LLM_MODEL_NAME、LLM_MODEL_BASE_URL、HEADLESS、ENABLE_TELEMETRY、LLM_MODEL_API_KEY，key 显示 ***REDACTED***。key 文件缺失特批：dry-run 分支用占位串 DRYRUN-PLACEHOLDER 顶上继续构建——不会执行所以无泄露面，离线验收做得了；非 dry-run 缺 key 直接 exit 2，不启动任何子进程。实测验收过：干跑日志假 key 零命中；四连冒烟最后一步就用不存在的 key 文件实证干跑可用。"

### 卡 13｜密钥全链：读→传→脱→验
- **怎么问**："key 怎么保证不泄漏？"
- **30-60 秒答**："四环。读取：key 文件支持单行（strip 即 key，历史行为）和 KV 两种格式——见到 KEY= 行按 KV 解析（注释行跳过，KEY 为空视为不可用凭据，MODEL/BASE_URL 行忽略、模型来自 provider 常量）；测试一律假 key（dummy-key-0123456789）。传输：key 只在内存、只经环境变量进子进程，命令行参数永远干净；同一批环境变量固定注入模型名 deepseek-v4-pro 与官方基址、关遥测 ENABLE_TELEMETRY=0（否则引擎 import 时初始化 Sentry）、HEADLESS、禁 uBlock 扩展（本机直连下载扩展不稳会拖死浏览器初始化）、本机回环代理绕行（防系统代理劫持 127.0.0.1）。脱敏：整串替换之外，长 key（≥16 字符）头尾各 8 字符片段也替换，全部换成 ***REDACTED***；三个落点——子进程输出写日志前、run 摘要里来自 JUnit 的失败消息（CLI 侧二次脱敏，评审抓出来的缺口，见坑卡 6）、dry-run 打印。验证：收口结论是双 key 全目录零命中；CLI 侧测试断言日志全文假 key 明文零命中（含 JUnit 失败消息路径）。密码层借上游配合：录制时即掩码成占位符，generate 填真实值——key/密码永不进 feature 原文之外的人工可读面。"

### 卡 14｜退出码职责：analyze 出报告即 0
- **怎么问**："退出码怎么设计的？"
- **30-60 秒答**："全命令统一 0/1/2/3/4/130。analyze 出报告即 exit 0——哪怕用例失败：报告产出是 analyze 的职责，用例成败由 run 的退出码承载（passed/dry-run 0、失败 1、子进程超时 3、JUnit 缺失/不可读 4、输入错 2、Ctrl+C 130）。analyze 再反映用例成败会和 run 重复且混乱，被否。"

### 卡 15｜子进程第一天定死（决策卡；完整故事见坑卡 1）
- **怎么问**："为什么非子进程不可？代价呢？"
- **30-60 秒答**："run 走独立项目根的子进程，第一天定死、不许进程内连跑。因为进程内有四个实证的坑（StaticLTM 单例串场、config 单例重置丢内存态、import 时时间戳目录混叠、PlaywrightManager 关闭竞态——坑卡 1 详述），工程上消除不了；且上游自己的 MCP server 也用子进程执行，照抄成熟先例。子进程白送三样：超时可杀（进程组整组 SIGKILL 连浏览器一起）、崩溃不传染（子进程崩不伤编排层）、天然可并行（每 feature 独立进程与项目根）。代价：每场景一次冷启动约 60 秒起，简单流程 7.3 万 token。被问成本账：总计划预算口径'单场景约 4.7 万 token / 0.13 美元、README 上限 0.20 美元/复杂场景、全实验 10-20 美元'；实测以实验报告为准——deepseek 前缀缓存大幅折扣实际费用，litellm 没该型号价格表所以成本显示不可用、以 token 计量。"

### 卡 16｜测试质量：81 + 54 条不是凑数
- **怎么问**："测试怎么摆的？质量如何？"
- **30-60 秒答**："81 条归因器 + 54 条 cli，全离线可跑：归因器用合成产物目录 + 假 analyzer + 0 字节 PNG；cli 把执行器全 mock、--polish/--llm 走接缝注 fake、record 用真实无头浏览器开本地页面。覆盖要点：13 条签名每条至少一个正例，断言类别/置信度/证据位置，S3 三分支、表序优先级、零模型 import 各有专项；LLM 层把未知引用、仅截图引用、非法重试、两次非法、异常两次、无 analyzer、回查定位符语义（一个函数参数化 14 例）、30 条上限丢弃顺序、摘录纯截断逐条覆盖；e2e 里机械校验'每条结论证据都能按定位符回查到原文且摘录是子串'。断言有效性做过变异测试：去掉 run 摘要二次脱敏 → 4 条红；放宽 test-data 值契约 → 1 条红（filled 虚报）。两模块评审均 REVISE 后修订通过：归因器 2 条必改（M1/M2）、cli 3 条必改（R1/R2/R3）——全部进了坑卡。归因器合并提交时全局 238 passed、cli 合并提交时全局 292 passed，最终全局基线 492。"

## 4. 踩坑故事卡（10 张卡覆盖 13 个坑：进程内四坑合一，其余各一）

### 坑卡 1｜核心故事卡：为什么非子进程不可——进程内四坑（原坑 1-4）
- **开场句**："这四个坑是我二开前源码审查实证出来的，不是背书。"
- **坑 A StaticLTM 单例串场**：静态 LTM 用类属性单例、整个进程只初始化一次——同进程跑第二个 feature 会拿到第一个 feature 的测试数据，结果互相污染且极难察觉。解法：每个 feature 一个子进程；run 的项目根也每 run 独立。
- **坑 B config 单例重置丢内存态**：同进程内重置配置单例会丢内存态，重置后再取实例不等于全新进程。解法：子进程天然全新 config。
- **坑 C import 时时间戳目录混叠**：时间戳在模块 import 时求值一次、被带进每个实例——同进程连跑共享同一 import 时刻，输出目录一族的证据混叠。解法：子进程各自的 import 时刻即各自的目录命名空间。
- **坑 D PlaywrightManager 关闭竞态**：浏览器管理器的关闭是发后不管的异步任务，与下一个场景的浏览器启动存在竞态。解法：子进程 + 独立进程组，超时对整组 SIGKILL 连浏览器子进程一起杀。
- **先例佐证**：上游自己的 MCP server 也回避进程内执行——起子进程跑引擎、300 秒超时杀。"上游自己都这么做"是照抄成熟先例的立论。
- **教训**：正确性坑无法工程消除时，架构约束要第一天定死。

### 坑卡 2｜子进程的代价：白送三样的对价（原坑 5）
- **现象**：每场景多一次浏览器/引擎冷启动，单场景约 60 秒起；token 成本显著——F1 简单流程实测 7.3 万 token；exp001 三十次执行共 4,109,386 token（均值 136,980/次）。
- **换来的**：超时可杀、崩溃不传染、天然可并行。
- **口径**：预算口径与实测口径分开说（见卡 15 追问）——实测以实验报告为准。

### 坑卡 3｜评审 M1：S3 语料二义——旗舰签名在真实运行会系统性失配（原坑 6）
- **现象**：spec 初稿把 S3 的扫描语料写成"失败消息（主）"，但源码数据流是导航轮次耗尽串会作为用户消息回灌 planner 会话、规范落点是 thoughts 文件——进失败消息/系统输出仅当 planner 恰好复述（LLM 行为不可依赖）。按初稿实现，S3 在真实运行大概率失配；而验收用例全用合成失败文本，测不出这个偏差。
- **修复**：spec 钉死 S3 按默认三字段顺序扫（两个特征须同字段），S12 语料并入 thoughts，并加数据流注记；测试补"主命中在失败消息而信号在 thoughts"用例。
- **教训**：签名表的"准"不只在匹配串逐字对，还在语料范围要跟数据流走。

### 坑卡 4｜评审 M2：摘录追加装饰文本会误杀合法 LLM 引用（原坑 7）
- **现象**：初稿让带轮次锚的截图文件名"随该轮摘录附上"，但回查要求摘录是所指轮次原文的子串——追加装饰文本必判摘录不符，凡带锚轮次的合法引用被系统性误杀 → 存活引用不足 → 最有归因价值的场景（元素找不到命中轮 + 对应截图）反而被压成无法定位。
- **修复**：截图单独打包为独立证据类型（回查走"存在即通过"）；thoughts 摘录定为纯截断，测试断言摘录就是原文前 400 字符。
- **教训**：回查不变量（子串校验）要反过来约束上游打包格式，两处规格必须同句措辞。

### 坑卡 5｜评审 R1：空事件不可达 + 测试接缝拿不到页面（原坑 8）
- **现象**：初稿假设"停止条件立即成立 → 零事件"，但录制器启动时固定推一条初始导航事件——事件数下限是 1，那条用例物理跑不通；接缝签名不让测试闭包拿页面句柄，无法驱动真实点击，另一条用例同样跑不通。
- **修复**：接缝改为把页面传进停止谓词（生产谓词忽略该参数）；空录制语义改成"事件数 ≤1 记告警、照常保存"。
- **教训**：审查纪律"用例清单里物理上跑不通的条目按必改计"，拦住了两条会逼实现者自行改设计的规格。

### 坑卡 6｜评审 R2：JUnit 失败消息不经 runner 脱敏（原坑 9）
- **现象**：runner 只对子进程 stdout 脱敏；失败状态下取自 JUnit 的失败消息不经任何脱敏——初稿"内容已被 runner 脱敏"失实，且原用例清单没覆盖它。这是 CLI 日志里唯一未过脱敏的外部文本面。
- **修复**：CLI 打印前自行再过一次脱敏兜底；测试用内嵌假 key 的失败消息断言日志明文零命中；变异测试验证去掉这行 → 4 条红。
- **教训**：密钥红线不能靠"引擎大概率不会回显 key"成立——外部文本进日志前一律过脱敏。

### 坑卡 7｜评审 R3：值契约与蒸馏器不一致会虚报 filled（原坑 10）
- **现象**：初稿接受 bool 值且未规定空白串，但蒸馏器丢弃 bool/null/空白——按初稿实现会"摘要 filled=1 但产物仍留占位符且无缺失警告"，缺值警告闭环在该输入类上失效。
- **修复**：CLI 值集与蒸馏器对齐（bool/null/空白＝未提供，对象/数组＝exit 2 列坏键）；变异测试验证放宽契约 → 红且 filled 虚报。
- **教训**：跨模块值契约以消费方为准逐字对齐，"宽收"制造摘要与产物的矛盾。

### 坑卡 8｜fixture 乱序：recorder 与 cli 子集连跑 6 红（原坑 11，终审新发现——"自知缺陷"必讲素材）
- **现象**：先跑 recorder 子集再跑 cli 子集，cli 的 6 条 record 用例挂——recorder 测试夹具的 session 级 browser fixture 全程持有一个同步 playwright 实例，与 cli 里的第二个同步实例冲突；反序（cli 在前）75 例全过。终审实测复现。
- **定性**：测试夹具的 session 级资源隔离问题，不是产品缺陷；官方入口全量单命令跑（默认字母序 cli 在前）恒绿，最终全局基线 492 passed。
- **处置**：终审不改代码（修复属一行 fixture 作用域调整）；README 写明"跑测试只用一条命令"。
- **讲法**：主动讲——这是"我知道自己测试套件的边界"的自知之明素材。

### 坑卡 9｜record 跨文档导航即中止（exit 2 不落盘）（原坑 12）
- **现象**：注入的录制器 JS 随文档销毁，多页站点一跳转、对录制器状态的查询就抛错——CLI 检测后记 error（文案内嵌已知限制说明）并 exit 2，不保存、不产脏数据。
- **取舍**：重注入 + 多段合并明确 Out of Scope；演示与评测选单页/本地页面；--manual（书签脚本）作为分页录制的替代路径。

### 坑卡 10｜run 中途 Ctrl+C 遗留子进程（原坑 13）
- **现象**：执行器未暴露协作式中断；run 期间 Ctrl+C 抛键盘中断且子进程组独立存活。
- **处置**：CLI 捕获后告警"子进程可能仍在后台运行，请等待自然结束或手动清理"并 exit 130；不为 CLI 单独改执行器（Out of Scope）。record 第二次 Ctrl+C 强制中止路径同理无自动化测试（信号要落进特定窗口才可复现，代码路径存在）。
