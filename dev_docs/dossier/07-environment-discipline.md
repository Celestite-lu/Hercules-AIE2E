# 07 — 环境踩坑与工程纪律（面试复习版）

> 复习定位：被问「踩过最深的坑」「怎么排查」「怎么保证协作质量」时的故事库与工程素养证据。素材收拢自 30 多份开发文档，覆盖模型密钥、网络系统、macOS 工具、测试 git、上游契约、视频制作六个域，共 30 张坑 + 18 条纪律。只背故事和数字，不背出处。

## 1. 这一页讲什么 + 本档案复习法

这一页把散在 30 多份开发文档里的环境坑、工具坑、流程纪律收拢成四层：10 张王牌坑卡（能脱稿讲 45-60 秒的完整故事）、一张 19 条的速查大表（被追问时 10 秒内调出）、12 张纪律速答卡、一页必背数字。

复习顺序：先把 §2 的 60 秒主线背到脱口而出 → 王牌卡每张练到「现象一句话、定位一句话、根因一句话、修复一句话、金句收尾」的节奏 → 速查表扫两遍记住坑名 → 必背数字过一遍（数字是这页最容易被突击检查的部分）。

如果只备五张卡，按这个序：NLTK 语料挂死（py-spy/lsof 定位法）、裸 ChatOpenAI 四键注入、max_tokens no-op（配置在位≠生效）、session 级 playwright fixture 乱序误红、macOS 系统代理劫持回环。总原则一句话：**配置在位 ≠ 生效；挂死别猜，看栈看连接；健康检查必须复用生产路径；机械复核替代自觉。**

## 2. 60 秒主线

被问「这个项目工程上最难的是什么」或「说说你的工程纪律」，完整口头回答：

> 「工程上最难的是三类环境的不确定性，以及怎么在不确定里保证实验和协作可信。
> 第一类是外部依赖。付费模型的余额耗尽会伪装成普通失败格烧掉重试预算——我们的顺序是先熔断、再预检、最后才烧预算；换模型时把 provider 做成开关，默认行为逐字节不变。
> 第二类是系统环境。NLTK 语料在受限网络下把进程挂死，我不猜：py-spy 看栈、lsof 看连接，五分钟定位，修复就是预装语料一行；macOS 系统代理会劫持 127.0.0.1 回环，凡对 localhost 发请求的代码一律显式禁代理。
> 第三类是隐性契约。session 级 fixture 和 CLI 的 sync 实例互斥，特定子集顺序误红 6 条但官方入口全绿——要能当场讲清这是夹具资源隔离问题、不是产品缺陷。
> 纪律层面三件事兜底：密钥从文件到屏幕全链脱敏，每轮收口双 key grep 零命中；核心目标优先，边界问题写进 Out of Scope 不打转；改上游引擎全部 flag 化默认关、off 档 golden 逐字节锁定，保证每一点提升都能和上游基线干净对比。」

## 3. 决策速答卡（12 张）

### 卡 1：密钥全链——从文件到屏幕的四道闸
- **面试官会怎么问**：「key 怎么管理才不泄漏？」「密钥安全怎么做的？」
- **30-60 秒回答**：
  先想清楚 key 有四条泄漏通道：被 git 提交、进 argv（ps 可见）、进日志和 manifest、进生成的配置文件。四道闸各堵一条。一，`LLM-Key.txt`、`.env.local`、`PLAN.md` 全部 gitignore，命令内联 `$(cat LLM-Key.txt)` 读取，key 不落第二份持久化。二，key 文件支持单行和 `KEY=` 键值两种格式解析（键值格式忽略注释空行、空值明确报错），所有测试用临时假 key、从不读真实文件。三，key 只经 subprocess 的 env 注入，子进程输出先过 `mask_secret` 再落盘，CLI 摘要二次脱敏。四，生成盘上的 `agents_llm_config.json` 永不含 key——写盘函数对含 key 配置直接抛错。最后机械复核：每轮实验收口跑同一条红线命令——`KEY=$(cat LLM-Key.txt)` 后对 `dev_runs`、`record2gherkin`、`tests`、`dev_docs` 四个目录 grep -rl，推送 GitHub 前再复跑一次；双 key 的实值加 8 字符前/后缀 grep 全部零命中。实测过假 key 明文 grep 为 0、`***REDACTED***` 占位符命中 1 行——脱敏确实在工作。
- **追问预案**：「为什么信 grep？」→ 不是信自觉是信命令：同一条红线每轮必跑、输出可复现；脱敏不是一处 if，是全链纪律。「测试会不会读到真 key？」→ 不会，测试全用 tmp 假 key，真实 key 文件只在命令行内联读取这一处出现。

### 卡 2：文档固化规程——缺一件视为未完成
- **面试官会怎么问**：「你们怎么保证开发过程可追溯？」「为什么这么多文档？」
- **30-60 秒回答**：
  每个模块收口必须交齐 plan、spec、review、test-report 四件套，缺一视为未完成。spec 的标准是「实现者读完不再需要做设计决策」；review 只出 PASS 或 REVISE 两种结论；test-report 必含三件套——测试命令与结果、已知问题清单（recorder 12 条、distiller 4 条、evaluation 18 条、attributor 23 条、cli 11 条、benchmark 10 多条）、格式化与脱敏复核。已知问题清单本身就是「审查→修复闭环真实发生过」的旁证。
- **追问预案**：「文档会不会拖慢迭代？」→ 会，但它换来两件事：任何数字能追到一手报告；跨会话的子代理协作不靠口头。「历史结论改了怎么办？」→ 历史文档不改写，更正以新文档固化。

### 卡 3：Git 与代码边界纪律
- **面试官会怎么问**：「多人协作怎么分工？」「怎么保证不把主仓库改坏？」
- **30-60 秒回答**：
  三条边界。第一，git 权责单一：子代理不做任何 commit、branch、merge，全部由总编排统一操作；功能在新分支开发、测试通过后合 main，合并后总编排再启动独立分析复核。第二，提交可追溯：约定式提交 `feat(...)`/`fix(...)`，决策日志和 git 历史逐条对得上。第三，代码包边界：二开新代码只进 `record2gherkin/` 和对应 tests 目录，不改上游主包（明确的接线点除外、逐个申报）；black 200 列加 isort，Python 用 logger 不用 print；实验产物进 gitignored 的 `dev_runs/`，结论才进文档。
- **追问预案**：「为什么子代理不让碰 git？」→ 防的是并行会话互相踩工作区；集中提交让合并质量有人兜底。

### 卡 4：核心目标优先（最高原则）+ 收尾禁重构
- **面试官会怎么问**：「需求边界的长尾你怎么处理？」「怎么防止过度设计？」
- **30-60 秒回答**：
  绝不在低收益边界问题上打转。边界情况一律写进 spec 的 Out of Scope 或 test-report 的已知问题清单，核心功能完成后再用测试案例完善；审查只拦「会导致核心目标失败的问题」，不吹毛求疵——审查的产出是收敛，不是完美。收尾同理：终审结论是「演示前不做任何重构」，连一行 fixture scope 的修法都留而不改，因为收尾阶段稳定性大于完美性。
- **追问预案**：「边界问题都记在哪？」→ 两个登记处：spec 的 Out of Scope 和各模块已知问题清单，都能指给面试官看。

### 卡 5：引擎 flag + golden 锁定
- **面试官会怎么问**：「你改了执行内核，怎么保证没改坏上游行为？」「怎么和基线公平对比？」
- **30-60 秒回答**：
  对上游引擎的所有改动三条约束。一，全部 flag 化且默认 off，off 档就是上游现状。二，默认路径用 golden 逐字节锁定：迁移前后对同一棵固定合成树抓 golden 留档，`json.dumps` 输出要求逐字节相等；补丁层同样有 off 档 golden。三，回归守卫常备：引擎侧测试 stash 前后对照各跑一次 12 passed，焦点组 4 个文件 26 passed，判分链 diff 审计 0 行。原则一句话：我的每一点提升都能和上游基线干净对比，且每个改动可以单独 revert。
- **追问预案**：「为什么逐字节而不是语义相等？」→ 语义相等靠人判，逐字节相等靠命令判；判分链 0 行 diff 是分数可信的前提。

### 卡 6：测试门禁
- **面试官会怎么问**：「测试基线怎么定的？」「别人克隆你的仓库能跑吗？」
- **30-60 秒回答**：
  三条。第一，只认一条命令：全量测试只有官方入口单命令，因为 recorder 在前的子集乱序会因 session 级 fixture 冲突误红 6 条——演示永远用官方入口。第二，口径注明环境：492 全绿是本机口径；新克隆环境有 12 例依赖 gitignored 录制产物的测试会 skip——skip 而非 fail，仓库附重建命令，被追问以现场实跑为准。第三，计数必须可复现：所有测试数量以 `--collect-only` 逐模块实测为准（492 = 21+68+77+81+54+191），引用前先跑命令、不抄看板——看板数字漂移过（67 实际 68、292 过期后残留）。另外对审查必改项做变异验证：临时改坏实现、对应用例必须红、复原并校验 sha1 不变——防「断言无效的假绿」。
- **追问预案**：「为什么 12 例不把产物提交进 git？」→ 大产物污染仓库是设计决策，代价用「skip+重建命令」支付，不用「红」支付。

### 卡 7：审查只拦致命问题
- **面试官会怎么问**：「你们的 review 标准是什么？」「审查会不会变成形式主义？」
- **30-60 秒回答**：
  审查子代理只拦「会导致核心目标失败的问题」，不吹毛求疵。理由是审查的产出应该是收敛而不是完美：吹毛求疵会让实现者在低收益边界上空转。但「只拦致命」不等于软弱——审查要有牙齿：独立复审抓出过真问题（文件写事件、快照归因缺陷、测试顺序陷阱），抓出来才算数。
- **追问预案**：「小问题谁管？」→ 已知问题清单登记，攒到核心功能完成后再清，不阻塞主线。

### 卡 8：子代理协作规程
- **面试官会怎么问**：「多个 agent 并行开发怎么保证质量？」
- **30-60 秒回答**：
  五条：开工前必读开发规约；每模块四件套缺一视为未完成；子代理零 git 操作、总编排统一提交；审查只拦致命问题；合并后由总编排启动独立分析子代理复核。配套分工：总编排负责计划、决策与合并，子代理按模块领任务，实验产物放 gitignored 的 `dev_runs/`，结论固化进 dev_docs。
- **追问预案**：「子代理之间冲突怎么办？」→ 包边界隔离（各自只写自己目录）+ git 集中操作，物理上避免并行写冲突。

### 卡 9：演示规避清单 R1-R7
- **面试官会怎么问**：「现场演示你怕什么？」「怎么保证 demo 不翻车？」
- **30-60 秒回答**：
  七条规避清单，按翻车概率排序。R1：录制注入的 JS 随跨文档导航销毁——绝不现场录多页站点，用本地单页或 file://，异常路径也是干净退出（exit 2 不落盘）。R2：`--polish`/`--llm` 真机未验收，演示不开。R3：真实执行要 key、60 秒起步、简单流程约 7.3 万 token——现场只用 `--dry-run` 秒级版，配固化产物和录屏兜底。R4：只用官方单命令跑测试（乱序误红 6 条）。R5：测试口径固定说「本机」，新克隆有 12 例 skip。R6：脚本驱动录制动作间隔至少 450ms，用默认节奏。R7：macOS 系统代理劫持回环——演示机异常就关系统代理或用 file://。外加一条收尾纪律：演示前禁重构，稳定性优先于完美。
- **追问预案**：「为什么不干脆全修好再演示？」→ 收尾阶段每一次「顺手修复」都是新风险面；已知问题登记比临场改代码便宜。

### 卡 10：数字与归因诚实
- **面试官会怎么问**：「你的数字可信吗？」「有没有发现自己错了的时候？」
- **30-60 秒回答**：
  三件事。第一，数字逐字一致：演示视频表格帧上 9 个数字与实验报告逐字视觉核对；报告内禁止无出处的数字；口径主动带限定词（单 demo 单模型、6 格样本不给点估计）。第二，归因敢往低了改：发现 max_tokens 注入实际是 no-op 后，我把自己报告里的「改进」修正为无效、摘除 flag，把超时 41→21 的功劳改记给有逐格证据的 planner 双层超时；引用 81.6% 这类外部数字前先克隆仓库、核对原文，数字可比前先对齐观察方式、判分方式、任务集、样本量四要素——追到一手出处后废弃整条二手叙事并固化更正。第三，历史文档不改写，更正以新文档固化。
- **追问预案**：「max_tokens 那事怎么发现的？」→ 端点实测：768 的配置实际产出 19,349 token——「配置声明在位」和「配置真正生效」是两回事，注入链验证过也不算数，要打到端点看产出。

### 卡 11：防作弊纪律——宁可掉分不洗分
- **面试官会怎么问**：「benchmark 怎么防止刷分？」「分数怎么保证干净？」
- **30-60 秒回答**：
  页面原生奖励是唯一权威，不设 LLM 裁判；每轮做五类作弊扫描；实验前后各做一次安全审查。真出过事：r2 有一次绕过扫描的事件，按预登记契约把 10 格无效化压分——官方口径 58/125=46.4%，剔除无效格后的干净口径 55/115=47.8%。看起来反直觉，但分数的可信性就是实验的全部价值：宁可压分，不洗分。
- **追问预案**：「为什么不修好再计分？」→ 修复本身会引入新变量；按预登记契约处理才能对所有人可复现。

### 卡 12：预算与配速纪律
- **面试官会怎么问**：「API 花费怎么控制？」「实验跑崩了怎么办？」
- **30-60 秒回答**：
  预算护栏计划期和运行期双拦截：exp001 是 pilot 4 + full 30 + 重试 5 = 39，不超 40 红线；benchmark 累计 cap 144、红线 142 格 / 20 美元。基础设施重试只限 timeout 和 no_junit，用例失败绝不重跑——失败是数据不是故障。执行侧分段跑加 429 熔断配速，断点续跑就是重跑同一条命令；禁止拆实验 ID 分窗记账（护栏是纪律条款，跨目录记账靠人工盘点）。护栏强度按实际实现如实分级披露，不夸大。
- **追问预案**：「为什么用例失败不重跑？」→ 重跑会破坏「每格一次诚实执行」的口径，把运气算进分数；缺预算才是故障，失败不是。

## 4. 踩坑故事卡（30 张，两层）

10 张王牌卡是「踩坑经历」类问题的主力弹药，按「现象→定位→根因→修复→教训」讲；其余 19 条进速查表，被追问时能 10 秒调出即可。

### 王牌卡 1：「挂死别猜——py-spy 看栈，lsof 看连接」（NLTK 语料 CDN 挂死）
- **什么时候讲**：被问「讲一个你排查过的最难的问题」「进程挂死怎么定位」「生产环境卡住怎么办」。
- **45-60 秒讲述**：
  benchmark 第一轮全量，有 3 个格子进程活着、日志零进展，一直耗到引擎 600 秒超时判负。我先做排除法：三个格子的共同点是连一个 agent 轮次都没产出——排除模型规划问题；进程 CPU 接近零但不退出——排除死循环，像是在等什么。然后两个命令定性：py-spy 对挂住进程抓调用栈，主线程停在 NLTK 分词语料下载的读取里；lsof 看文件描述符，一条对外网络连接挂着。全程约 5 分钟。根因：无头环境第一次跑触发了 NLTK 语料的自动下载，CDN 不通就无限等待。修复一行：r2 起语料预装进环境，再没复现。
- **收尾金句**：「挂死别猜——py-spy 看栈、lsof 看连接，两个命令把『卡在哪』变成事实；环境依赖的『首次自动下载』在受限网络下全是定时炸弹，能预装就预装。」

### 王牌卡 2：「本机回环 ≠ 免疫代理」（macOS 系统代理劫持 127.0.0.1）
- **什么时候讲**：被问「网络问题怎么排查」「测试在开发机能过在别人机器挂」。
- **45-60 秒讲述**：
  macOS 开着系统代理时，sweep 对本地服务的 `/__control`、`/healthz` 调用全部 502。定位：Python 的 urllib 默认读系统代理，ProxyHandler 把 127.0.0.1 的回环请求也转发给代理再被拒——macOS 系统代理默认不豁免回环地址；而 playwright 的 chromium 走自己的网络栈，完全没事。同一族坑还有个变体：有 CLI 用例依赖「连 127.0.0.1:1 被拒」这个行为，代理转发后返回了页面，断言失败但不挂起。修复两层：代码里凡对回环发 HTTP 的地方统一显式禁用代理；benchmark 线还踩到 chromium 层也跟系统代理、本地任务页直接加载成 chrome 错误页——于是加了默认关闭的门控，环境变量（`CHROMIUM_PROXY_BYPASS_LOOPBACK`）开启时给 chromium 加 `--proxy-bypass-list=<-loopback>`，只旁路回环、外网照走系统代理。
- **收尾金句**：「对 localhost 发请求的测试，要么显式禁代理、要么用 file://，并且把这个假设写进已知问题清单——本机回环从不免疫代理。」

### 王牌卡 3：「key 和端点是绑定卖的」（GLM coding plan 403）
- **什么时候讲**：被问「接过新模型/新 provider 吗」「第三方 API 集成的坑」。
- **45-60 秒讲述**：
  deepseek 余额耗尽后切智谱 GLM coding plan，第一反应是拿通用 paas 端点去调 coding plan 签发的 key——直接 403 model_access_denied。根因：coding plan 走智谱独立的编码服务路径，普通 paas 端点根本不认这种 key；key 和 base_url 是一套绑定销售的。修复：GLM provider 的端点常量固定为 coding 专用地址 `https://open.bigmodel.cn/api/coding/paas/v4`，OpenAI 兼容、接口类型恒为 `openai`；预检也走同一 provider 配置；接入时 dry-run 先实测四个环境变量键。
- **收尾金句**：「换 provider 时，端点常量化加预检探测，比『先跑一格再报错』便宜得多。」

### 王牌卡 4：「余额是实验变量」（DeepSeek 402：重试格秒崩→熔断→预检→换模型）
- **什么时候讲**：被问「实验可靠性怎么保证」「跑批被外部服务搞挂怎么办」「为什么换模型」。
- **45-60 秒讲述**：
  r1 全量中 3 个格子的重试行因为 LLM 402 余额不足秒崩，烧掉基础设施重试预算，之后 deepseek 余额彻底耗尽。关键的认知转变：预付费余额耗尽是运维状态不是代码状态，没有熔断时它会伪装成「正常失败格」消耗重试池。修复分三层。先熔断：attempt 级三条件加 run 级连续 2 格失败即熔断，熔断标记用 `"402"` 裸子串匹配——误报方向只会「少重试、多熔断」，偏保守可接受；attempt 日志按尝试次数分目录防覆盖。再预检：1-token 探测，余额或连接异常直接 exit 3，不启服务不执行，并加 429 熔断配速。最后换模型：整体切 GLM coding plan（planner=glm-5.3，nav/helper=glm-5.3-flash），provider 做成 `--provider {deepseek,glm}` 开关，默认 deepseek 的行为逐字节不变，换模型造成的多变量混杂主动披露。
- **收尾金句**：「付费 API 的余额是实验变量的一部分；顺序永远是先熔断、再预检、最后才烧预算。」

### 王牌卡 5：「上游默认开的联网副作用，逐一盘点关停」（uBlock 下载卡死）
- **什么时候讲**：被问「复用别人的引擎/框架踩过什么坑」「供应链安全」。
- **45-60 秒讲述**：
  exp001 pilot 首跑复盘揪出三个基础设施问题，这是其一：上游引擎默认启用 uBlock 广告拦截扩展，浏览器启动时要联网下载扩展包，受限网络下下载超时直接打断初始化。修复：子进程环境固定注入 `ENABLE_UBLOCK_EXTENSION=false`，和关遥测（`ENABLE_TELEMETRY=0`）、headless 一起成为标准执行环境；顺带收益是外呼面收敛——harness 侧外联只剩模型端点加 127.0.0.1（demo 站无广告，禁用无副作用）。修复后 pilot003 三格全过。
- **收尾金句**：「复用上游引擎时，它默认开的每一个联网副作用——遥测、扩展、更新检查——都要逐一盘点并关停；这既是稳定性问题，也是安全外呼面问题。」

### 王牌卡 6：「macOS 没有 timeout——超时控制下沉到 Python」（GNU 工具假设）
- **什么时候讲**：被问「跨平台开发的坑」「shell 脚本踩过什么坑」。
- **45-60 秒讲述**：
  要在 shell 层做「限时执行并杀进程」，发现 GNU coreutils 的 timeout 在 macOS 默认不存在。选择不是 brew 装一个凑合，而是把所有限时杀进程都下沉到 Python 层：引擎超时 600 秒、评测 900 秒按参数传入，杀整个进程组，退出码和日志全都拿得到；CLI 的 Ctrl+C 也统一成 exit 130 加残留子进程告警。
- **收尾金句**：「跨平台脚本不要假设 GNU 工具在；超时控制下沉到 subprocess 层反而更可控——进程组、退出码、日志全能拿。」

### 王牌卡 7：「钉死窗口 ID，别信『当时谁在前台』」（录屏焦点被抢 + 中文窗口名）
- **什么时候讲**：被问「自动化做过什么有意思的事」「UI 自动化的坑」「macOS 深坑」。
- **45-60 秒讲述**：
  做演示视频的终端实录，连翻两次车。第一次 screencapture 用全屏模式——它跟随焦点，录出来是前台另一个应用（ZCode）的窗口，作废。第二次学乖了按窗口属主名过滤，结果拿到空列表：macOS 中文系统里 Quartz 看到的窗口属主叫「终端」不叫 "Terminal"，本地化显示名骗过了匹配——这就是第二次录出空结果的根因。两次翻车换来的定式：screencapture 按窗口 ID 录（`-v -l窗口ID`），与焦点无关；窗口匹配要么用 ID、要么枚举比对本地化名。
- **收尾金句**：「自动化要钉死对象标识，不要依赖『当时谁在前台』；系统 API 返回的名字是 locale 的函数。」

### 王牌卡 8：「fixture 的 scope 是全局契约」（乱序误红 6 条）
- **什么时候讲**：被问「测试稳定性」「pytest 深坑」「测试红了但代码没问题怎么回事」。
- **45-60 秒讲述**：
  有人把测试拆成子集跑：recorder 目录在前、cli 在后——cli 的 6 条 record 用例全红；把顺序反过来，75 例全过；而官方入口单命令全量跑，当时的 292 例全绿。定位：recorder 的 conftest 里有个 session 级 playwright fixture，全程持有 sync 实例；而 CLI 里会起第二个 sync 实例——playwright 的 sync API 同一线程不允许两个并发上下文，benchmark 侧的浏览器 fixture 也因此设成 function 级。定性要清楚：这是夹具资源隔离问题，不是产品缺陷。处理也很克制：演示只用官方单命令；真修法是一行 fixture scope 从 session 改 function，但收尾阶段刻意不改代码。
- **收尾金句**：「fixture 的 scope 是全局契约；能当场讲清『为什么乱序红、官方入口绿、为什么先不修』，本身就是测试素养的考点。」

### 王牌卡 9：「少注一个键，125 格 headline 报废」（裸 ChatOpenAI 只认 OPENAI_API_KEY）
- **什么时候讲**：被问「配置系统踩过什么坑」「『明明配置了怎么不生效』这类问题」「code review 抓过什么」。
- **45-60 秒讲述**：
  r2 的角色路由改走配置文件后，review 时沿源码追出一个隐雷：如果子进程环境只注 `MODEL_API_KEY`，planner 构造时就会抛缺 key，125 格 headline 直接报废。链路三层。一，配置管理器文件加载成功后直接 return，env provider 完全不注册——File 大于 Env 是源级覆盖，不是按键合并，与直觉相反。二，文件里省了 model_api_key，产出的配置里就没 key。三，planner 是裸构造 `ChatOpenAI`，不经统一的 `create_chat_model` 工厂，而仓库锁定的 langchain-openai 里 ChatOpenAI 只从显式参数或 `OPENAI_API_KEY` 解析 key，不读 `MODEL_API_KEY`——后者只有工厂消费（救 nav/helper）。r1 能跑只是因为 env 路径恰好把 key 变成了 config 内字段，切到文件路径后这条通道消失了。修复：该路由开启时子进程环境恰好注四个键（配置文件路径、引用键、`MODEL_API_KEY`、`OPENAI_API_KEY`，后两者同值），测试断言到「多一个键都不行」；key 仍只走 subprocess env 红线。
- **收尾金句**：「『声明在位 ≠ 生效』有第二种形态：env 注入按各消费端自己的路径生效，必须沿源码核到构造函数才算数。」

### 王牌卡 10：「先跑契约探测，再按文档设计」（上游 JUnit 落盘路径）
- **什么时候讲**：被问「怎么接手不熟悉的上游代码」「文档和实现不一致怎么办」。
- **45-60 秒讲述**：
  取 JUnit 报告时按上游文档口径设计成 `--output-path` 直落结果文件；离线一测，上游实际返回的是项目输出目录下按 import 时刻时间戳生成的 run 子目录——文档口径和实现脱节，`--output-path` 只落到配置项，不影响取数路径。修复：定位改两级查找——先查直落路径，再查 run 子目录通配、取最新修改时间兜底，新单测把这个实测契约锁住；项目根目录参数仍是唯一有效的 run 隔离手段；以后发现新落点只需扩一个查找函数。
- **收尾金句**：「复用上游前先跑一次契约探测，把实测行为写进 spec——别按文档想象设计取数路径。」
