## 1. 这一页讲什么 + 本档案复习法

1. 完整记录 MiniWoB++ 全量 125 任务四轮基准迭代：官方 last-wins 口径 43.2% → 46.4%（干净口径 47.8%）→ 47.2% → **61.6%**，逐轮给出设定、改动、结果、逐格归因、诚实披露与踩坑。

## 2. 60 秒主线

（被问"讲讲你的四轮迭代"，背这一段。）

> "我在 MiniWoB++ 全量 125 个任务上做了四轮基准迭代，官方 last-wins 口径从 43.2% 涨到 61.6%，每一格涨分都有日志证据。r1 是基准轮，43.2% 本身不是重点，收获是画像：93% 的墙钟耗在 executor 微决策轮数上，另有三大放大器——页面终局后平均空转 273 秒、重导航把页钟续到 +584 秒、helper 60 秒双超时级联——还有 5 格判分瑕疵白丢分，后面三轮全部打在这张画像上。r2 落地判分中立修复加 C1-C7 改进包，涨到 46.4%（干净口径 47.8%），但同一轮因为 deepseek 余额尽换了 GLM，多变量混杂我如实披露，涨分不能全记改进包头上。r3 修延迟链，超时 41→21、无效格清零，但分数只到 47.2%——复盘时发现我声明的 max_tokens 上限根本没生效（768 配置实测打出 19,349 token），我把它改判 no-op、功劳改记 planner 超时链拆除；分数持平是真实机制增益 +5 格被单 seed 噪声 −4 格抵消的持平之谜。r4 修一个死分支——md 交互元素表把 div/span 整批过滤掉了——+17 格有逐格点击日志实证，77/125 = 61.6%，越出公开可比带 47-60% 的上沿；净 +18 格已超出 ±10 格噪声带，全程配了判分压分证据和三次把功劳改低、把数字改对的诚实修正。"

### 2.1 逐轮底账（设定 / 改动 / 结果 / 归因 / 披露的事实层，速查用）

**r1（2026-09-22，43.2% = 54/125）——基准轮**

- 设定：Hercules 执行内核（planner→executor 三节点 LangGraph），全角色单模型 deepseek-v4-pro；意图经 Gherkin 中转（Given=带 seed 任务 URL / When=指令原文 / Then=任务完成）；md 属性蒸馏 DOM（文本档非视觉）；页面 episode 240s（原版 10s，放宽已披露）、引擎 600s；判分用页面原生 `WOB_RAW_REWARD_GLOBAL > 0`，无 LLM 裁判；实验前 YELLOW → P0 加固（封死 HUD 奖励显示与 START 重开层）→ 实验后 GREEN，五类作弊证据全零。每任务单 seed 单次、seed 确定性派生，支持断点续跑复现。
- 可比性限制四条（主动披露）：模型非 GPT-4、计时放宽、Gherkin 中转、单 seed 单次。
- 结果三口径：官方 54/125 = 43.2%；首实例 59/125 = 47.2%（4 no_goal + 3 no_reward 计 0）；零重导航子集 37/60 = 61.7%（有选择偏差，只作诚实性指标）。成本 12.9M token、wall ≈ 336s/格。对照公开可比带 A 档 47-60%（零样本/文本-DOM/GPT-4 级）：首实例触及带内下沿，官方略低于带。
- 失败拆桶 A-F（71 未过格）：A 判分瑕疵 5（页面 raw>0 已到手，被 600s 引擎超时/重试崩溃覆盖白丢分：click-collapsible-2-nodelay、click-pie、login-user-popup、multi-layouts、use-colorwheel-2 raw=0.537）/ B 引擎 600s 击杀 23 / C 页面 240s 到点 25（页钟到期 WOB 回 −1、引擎正常收尾）/ D 立即判负或答错 11 / E no_goal 4（3 empty utterance + 1 goal JS 报错）/ F no_reward 3（drag-cube、draw-line、resize-textarea）。对账：报告"超时 29"是含 5 个重试行的 status=timeout 行数（130 行），去重后实质 600s 击杀 25 格；真超时现象 B+C = 48 格（38.4%），最大单一失分来源。
- 计时分解（10 个引擎杀格逐格实测）：planner LLM 242s ≈ 4% / 实测工具执行 151s ≈ 3% / 其余 ≈93% 是 executor 逐轮 LLM 微决策（每轮仅 40-1000 token，一次 hover/click/取 DOM）；通过格基线（12 格均值）executor 18.2 轮、planner 3.9 轮、span 158s；被杀格平均 35-60+ 轮 vs 通过格 18 轮——差距在轮数不在单轮延迟；最极端 email-inbox-forward 101 轮/span 581s。架构反思修正了报告初判：planner 轮次不是延迟源（超时格均值 3.2 轮 vs 通过格 3.7），真凶是 executor"动作后强制重感知"双倍轮次——超时格均值 51.3 轮 vs 通过格 19.9、"changed browser state" 链断裂均值 25.1 次 vs 通过格 6.4 次（每断裂一次强制停链→重感知→再来一轮）；全语料轮间中位 5s/均值 9.0s/p90 23s（n=2981）；单步 nav 上限 50 轮且无时间预算。
- 三大放大器：①僵尸空转——页面终局后引擎不读 done/reward 终态，平均空转 273s（详见第 4 节故事卡）；②重导航复位 240s 页钟——reload 即重开 WOB episode 计时器，email-inbox-forward 16 次导航把页钟"续"到 +584s 才到期（email-inbox/-delete 553/581s），页级预算对该类格完全失效；③helper 60s 双超时级联（7 格，详见第 4 节故事卡）。
- 重导航归因：61/125 格重导航 ≥2 次（最多 15 次），格内洗白 0 格，6 格反向自伤（其中 5 格即 A 桶判分瑕疵），1 格直接致败（email-inbox-delete 首实例 raw=1，被 8 次重导航拖到 −1）；93% 重导航走同 tab reload（249/267），prompt 还在主动教"刷新=重开 URL"。结论：封死通道不改变任何已得成绩，只把隐藏时间税显式化——接近判分中立。
- 战略产出——9 假设与组合预期：H1 判分修复 +4.0pp（+5 格，43.2→47.2，判分中立）；H2 重导航治理（sessionStorage 单次开局为主 + prompt 撤销刷新教学为辅）；H3 延迟压缩 +3~8pp；H4 Gherkin 模板上下文 +2~5pp；H6 分角色模型路由；H7 240→480s 对照（上界 20pp、现实 +4~10pp）；H8 停在首个终局奖励；H9 运维（402 熔断 + per-attempt 日志）。主推组合（不含 H7）预期 50-56%；保守组合 47.2-48.2%；主推+H7 ablation 口径 54-62%。HUD 加固移除成功信号 → 验证步注定空转（multi-layouts 页面通过后 46/64 轮、use-colorwheel-2 56/65 轮），列为 r2 修复方向。
- 披露与坑：完成幻觉 29/36（agent 自报成功而页面判负，TERMINATE 无页面 reward 校验）；可恢复性矩阵（每格只记一个主杠杆）保守 22 → 76/125 = 60.8%（A 档带上沿）、上界 49 → 103/125 = 82.4%——杠杆不可加总兑现，此为数学上界；3 格重试行因 LLM 402（余额不足）秒崩；attempt1 日志被 attempt2 覆盖；E/F 桶计数笔误（6 应为 7）；能力盲区定性：拖拽/绘制/选区 14 格（无 drag 工具）、画布几何/视觉 11 格（文本 DOM 天然盲区）、email-inbox 多步记忆 10 格（轮数爆炸 + 重导航清进度）。

**r2（2026-09-23，46.4% = 58/125；干净 55/115 = 47.8%）——C1-C7 改进包 + 换 GLM**

- 改动清单（逐条披露，换模型是多变量混杂）：
  1. **模型更换**：deepseek-v4-pro → GLM（planner=glm-5.3、nav/helper=glm-5.3-flash，coding plan 端点；起因 deepseek 余额尽）——多变量混杂，r1→r2 差异不能全部归因于改进包，每条归因逐项标注。
  2. C1a 判分中立修复：页面奖励优先于引擎 infra 状态（r1 的 H1 落地）——复审实证零"页面已过被判负"，2 个 timeout 审计格翻正（click-shape raw=1@92s、odd-or-even raw=1@62s）、4 格 junit 不再否决页面。
  3. C2 终局信号：中性 EPISODE ENDED cue——零提前放弃（300 处 cue 全部晚于终局）；但引擎不停车原样保留（40 超时格 zombie 中位 339s），cue 未接入 terminate 判据。
  4. C3 单次开局（sessionStorage）：**多导航格 61 → 16**；16 个 nav≥2 败格无一靠重导航翻正——重导航不再产生分数，只产生墙钟。
  5. C4 延迟包（markers_only 重感知/步级预算/prompt 修订）——未抗住 GLM-flash 肥尾。
  6. C6 extra_tools：drag 工具启用——61 次调用 0 次成功、0 格因此通过（工具把非 md= 前缀选择器整个包进 `[md='…']` 致 ValueError；且拖拽源根本不在 md 交互元素表），净效果记 −0（净负风险）。
  7. C7 模板上下文 + goal 预读非空等待：no_goal 4→1（r1 老 bug 修复）。
  8. 运维包：NLTK 语料预装、chromium 回环代理旁路、429 熔断、--max-cells 配速（两段分段执行）；GLM 额度消耗低于预期，r3 起 chunk 上限翻倍、单段提至 140 格级、以 429 熔断兜底。
- 运维三雷：①key 配置链——以"GLM/DeepSeek 两 key 对 dev_runs 全目录双 grep 零命中"收口；②系统代理回环（chromium 走系统代理打回环）——以回环代理旁路修复；③NLTK 挂死（r1 挂死根因）——语料预装根治。
- 结果：官方 58/125 = 46.4%（r1 +4 格）；干净 headline（剔除 11 个安全事件格）55/115 = 47.8%，触及 A 档下沿；**首实例 58/125 = 46.4% 与官方完全相等——零洗白，两口径首次统一**；零重导航子集 55/102 = 53.9%。成本 9.08M token（GLM coding plan 额度内）。失败结构：超时 41（最大桶）、官方失败 23、no_goal 1、no_reward 2（合计 67 格）。
- 结构性迁移：r1 最大桶是"引擎 600s 击杀 + 判分瑕疵"；r2 的 41 个超时格**全部是页面 240s 时钟先杀**（C1a 生效后页面通过不可能再被覆盖）——约束从"引擎限时"移到"页面 240s 时钟 × 单步延迟"。
- 归因与混杂披露：任务级迁移 r1fail→r2pass 10 格、r1pass→r2fail 6 格 → 官方净 +4；10 个新过格中 3 格是 r1 D 桶理解错误（choose-date-easy、click-checkboxes、click-tab-2-medium），C 包无对应杠杆——**指向 GLM 能力**；倒退 6 格多为 r1 靠 deepseek 速度险过的格。模型混杂双向都在，不可分。
- GLM 肥尾（r2 核心新发现）：>800 token 长补全 turn 轮间中位 46.2s/p90 80s（n=3197 executor turn）；**10.3% 的 turn（>500 token）消耗全部 executor 墙钟的 38%**（14426s/37635s）。C4 延迟包被肥尾抵消；r1 的 helper 60s 级联换位成 r2 的 planner 90s 级联——25/41 超时格发生 ≥1 次 planner 90s 超时（draw-circle 10 次），2 格因此秒死（click-shades、drag-shapes-2，零执行判负）。
- 披露与坑：完成幻觉 15/23（65%，绝对数降占比仍高）；可恢复性矩阵保守 21 → 79/125 = 63.2%、上界 53 → 111/125 = 88.8%（数学上界）；480s 预估上界 16 格 / 保守 6 格（僵尸期仍正确执行的计时敏感格）；坑：reward 事件含跨阶段陈旧数据需按 (task, seed)+run 窗口过滤、drag_and_drop 契约错配浪费 61 次调用各烧 1-2 轮。（W2 安全事件全案见第 4 节故事卡与 04 档案。）

**r4（2026-09-24，61.6% = 77/125）——md 终表扩展 + verify-before-done**

- 改动两项（均 flag 化默认 off + golden 锁定）：
  - **A `--md-extended`（md 终表过滤器扩展，主梁）**：死分支修复——交互元素提取逻辑里一个"'r' 键不存在"的过滤条件把 div/span 等非标准表单元素整批丢弃（更早的角色白名单只匹配 r 键，而 `rename_children` 从不被调用、该键从未存在——确为死分支）；r4 把 `flatten_interactive_nodes(extended=...)` 提到模块级，`extended=False` 逐字节复现 r3 行为；修复后 flatten 上限 150，实测全轮 md 表最大 129 < 150 无截断。
  - **B `--verify-before-done`（终止前校验，诚实性组件）**：terminate 前观察页面 reward；103 轮全部观察性质、零后续动作、裁决先于 verify 落盘。

### 卡 5 · 240s 边际（12% 兑现率）

### 卡 6 · 单 seed 方差三数（16.8 / 12.8 / ±10）

**面试官会怎么问**："为什么单 seed 单次？方差多大你心里有数吗？"
**30-60 秒回答**：三个数：同模型双轮（r2↔r3，只改机制不改模型）实测翻转 21/125 = 16.8%（r2 败→r3 过 11、r2 过→r3 败 10）；扣掉机制可归因的 5 格（drag×3、click-scroll-list、click-menu-2）后，纯单 seed 噪声翻转约 12.8%；整体表述为 ±10 格 / ±8% 绝对分的随机摆动带宽。按 flip=2p(1−p) 反推，边缘格（p≈0.5）占全网格约 26%（保守）~34%（含机制混杂口径）。推论：任何小于 ±10 格的轮间差异都不能直接当机制功劳——r3 的持平与 r4 的 +18 都对照这条带解读。
**追问预案**：

### 卡 7 · 多 seed 口径决策（majority-of-3 vs best-of-3 拒绝）

**面试官会怎么问**："方差这么大，为什么不跑多 seed？"
**30-60 秒回答**：多 seed 治"测量"不治"能力"，我拆成两个方案。majority-of-3 是归因稳定化工具：只跑边缘 21 格，噪声带从 ±10 收到 ±3，代价 3.5h 墙钟 / 4.3M token——这个待用户决策。best-of-3 已经拒绝：它能加 +4~7 格，但那是"每格三次机会"的口径红利，headline 掺水，不能要。全网格跑 3 次约 21h / 39M token，性价比也不值。
**追问预案**：

- r3 的可恢复性矩阵还算数吗？→ 算，但那是数学上界：保守 17 → 60.8%、上界 45 → 83.2%，杠杆不可加总兑现。

### 卡 9 · 教训清单精选

**面试官会怎么问**："这四轮学到的最重要的东西是什么？"
**30-60 秒回答**：挑三条硬的。①**机制受益面按机制算不按家族算**：r4 的 plan 只按 email+find-greatest 给改动记账，结果 12 格"不可寻址元素"外溢收益没进预期——预估收益时先问"这个机制触达哪些格"，不是"这个家族有几格"。②**声明在位≠生效**：768 的 max_tokens 配置注入成功，实测单轮打出 19,349 token——任何配置类改动必须实测行为差异，否则归因会挂到不存在的杠杆上。③**归因敢往低改**：超时减半从 R3-1 改记 R3-2；480s 预期从 +6~16 下调到 +1±1——用兑现率（12%）校准预估，而不是保住面子。另有一条主线：延迟治理的目标在轮数不在单轮，放大器会换位（helper 60s 级联 → planner 90s 级联 → executor 90s 停顿+肥尾），拆掉一个要盯下一个。
**追问预案**：
- 判分中立修复的定位？→ 它是第一优先级：页面奖励优先于进程超时这类"把口径执行对"的修复零争议、先行落地；能力增强与口径变更分开归因、分开陈述。
- 单 seed 的教训？→ 成绩永远带噪声带陈述，这是 16.8% 翻转率买来的习惯。

## 4. 踩坑故事卡

### 故事卡 1 · max_tokens no-op（王牌诚信故事，必第一张）

**什么时候讲**：被问"你有没有发现自己的结论是错的/后来怎么处理"（qa-bank Q22）、"配置改动怎么验证有效性"、"归因可信度"。
**45-60 秒讲述**："r3 我给 nav 补全加了个 768 的 max_tokens 上限，flag 在位、引擎注入链确认正常，超时也确实从 41 降到 21。实验后复审拿补全分布对账，发现 GLM 端点根本不把 max_tokens 当内容硬上限——768 配置下单轮实测打出 19,349 个 completion token，全轮 215 个 turn 超过 768，分布和 r2 完全同质。也就是说超时减半跟这个改动无关。我做了三件事：把报告和 manifest 修正为 no-op；把超时减半的功劳改记给真正起作用的 R3-2——planner 双层 150s 超时链拆除（r3 全部 21 个超时格 planner 超时 0 次，r2 两个秒死格复活）；把这个教训沉淀成'声明在位≠生效'——配置写入成功不等于行为生效，r4 若要真上限得换实现，比如客户端流式截断。"
**收尾金句**："功劳挂错杠杆比没有功劳更危险——19,349 这个数字教会我'声明在位≠生效'。"

### 故事卡 3 · email 家族四轮才通

**什么时候讲**：被问"你的方法有什么局限、后来怎么突破"、"举一个死磕到底的例子"。
**45-60 秒讲述**："email-inbox 家族 10 个格子 r2、r3 两轮全灭，合计 0/20，而且死法唯一且稳定：收件行、trash、star 图标不在 md 交互元素表里，一切 text=、css=、xpath=、index= 选择器全被包进 [md='…'] 然后 not found。我一度以为这是执行质量问题，r3 复盘确认它是全网格最大单一杠杆收益区，而且不是方差。r4 找到根子：交互元素提取里一个'键 r 不存在'的过滤条件把 div/span 等非标准表单元素整批丢弃——更早的角色白名单只匹配 r 键，而 rename_children 从不被调用，这个键从未存在过，是彻头彻尾的死分支。修复后 flatten 上限 150、实测全轮 md 表最大 129 无截断，email 立刻 4/10。"

### 故事卡 4 · GLM 肥尾发现（延迟治理打地鼠）

**什么时候讲**：被问"延迟优化怎么做的"、"LLM 应用工程的坑"。
**45-60 秒讲述**："r2 换 GLM 后，r1 的延迟包没扛住，因为冒出一个新形态：GLM 补全长度的肥尾。超过 800 token 的长补全 turn，轮间耗时中位 46.2 秒、p90 80 秒（n=3197 个 executor turn）；只占 10.3% 的 turn（>500 token）吃掉全部 executor 墙钟的 38%（14426s/37635s）。更麻烦的是放大器会换位：r1 是 helper 60s 级联，r2 变成 planner 90s 级联——41 个超时格里 25 个发生至少一次 planner 90s 超时，draw-circle 一格 10 次；click-shades、drag-shapes-2 两格直接零执行秒死。到 r3 拆掉 planner 超时链，肥尾又换位到 executor 侧：90s 停顿波及 21 个超时格里的 20 个，但单格量级更小，最大单次补全 3918 token（bisect-angle）。"
**收尾金句**："延迟治理是打地鼠——拆掉一个放大器，肥尾就从下一个口子冒出来，所以要盯轮数和补全分布，不是平均延迟。"

### 故事卡 5 · 僵尸空转 273s（含 r1 失败拆桶 A-F）

**什么时候讲**：被问"超时问题怎么定位根因"、"你的工程画像能力"。
**45-60 秒讲述**："r1 最大的发现不在分数在画像。71 个未过格我拆成六桶：A 判分瑕疵 5 格——页面 raw>0 已到手却被 600s 引擎超时或重试崩溃覆盖，白丢分，比如 use-colorwheel-2 页面已给 0.537；B 引擎 600s 击杀 23 格；C 页面 240s 到点 25 格；D 立即判负或答错 11 格；E no_goal 4 格；F no_reward 3 格。对账还发现报告的'超时 29'是含 5 个重试行的行数，去重后实质 600s 击杀 25 格，真超时现象 B+C=48 格、占 38.4%，是最大单一失分来源。这 48 格里藏着最贵的浪费——僵尸空转：23 次实质击杀里页面早已终局，而引擎不读页面的 done/reward 终态，之后平均空转 273 秒、合计 6280 秒约 1.75 小时；最狠的一格 login-user-popup 27 秒就通过了，之后又空转 573 秒。配套的还有重导航续钟：reload 会重开 WOB episode 计时器，email-inbox-forward 16 次导航把 240s 页钟续到 +584s 才到期。"
**收尾金句**："273 秒空转教会我：先问引擎有没有在浪费钱，再问 agent 聪不聪明。"

### 故事卡 6 · helper 60s 级联（从表象挖到机制）

**什么时候讲**：被问"举一个从表象挖到机制根因的例子"、"你怎么做根因分析"。
**45-60 秒讲述**："r1 有 7 个格子明确记载同一种死法（ascending-numbers、click-menu、daily-calendar、drag-circle、find-greatest、order-food、use-spinner）：单次工具调用遇到延迟尖峰被 60 秒掐断 → planner 把下一步改写成 'timed out, retry' → 重试或重导航把已到手进度清空；71 个败格里 32 格含这种改写。但我往深处挖了一层：延迟的真凶并不是 planner——超时格 planner 均值 3.2 轮 vs 通过格 3.7，不差；真凶是 executor'动作后强制重感知'的双倍轮次，超时格均值 51.3 轮 vs 通过格 19.9，'changed browser state' 链断裂均值 25.1 次 vs 6.4 次，每断一次就强制停链、重感知、再来一轮。全语料轮间中位 5 秒、均值 9.0 秒、p90 23 秒（n=2981），而单步 nav 上限 50 轮、没有时间预算。结论：差距在轮数不在单轮延迟——这条结论定了后面三轮延迟治理的主线。"
**收尾金句**："helper 只是按秒表计时的那只手，真正烧时间的是 executor 一轮一轮的重感知。"

### 故事卡 7 · 诚实修正另两案（锚点更正 + 笔误对账）

**什么时候讲**：被问"有没有发现自己的数字是错的"、"你怎么对待自己的报告"；与故事卡 1 连用凑齐三案。
**45-60 秒讲述**："除了 no-op，还有两案。第二案是 Agent-E 81.6% 锚点更正：我从 r1 起把它当同源架构的冲刺锚点，r1 报告写差 34-38 个百分点、r4 报告写差 20 个百分点；r4 期间专项核实发现 81.6% 其实是 HxAgent 的数字，而且四重口径不可比——偏科子集 5 任务族×25 实例、GPT-4o 多模态、每族 20 训练实例加 8 个 few-shot 经验注入、金标动作序列判分、±34.6 方差；Agent-E 从未发表过 MiniWoB++ 数字，唯一的数字是 WebVoyager 73.2%，还是 GPT-4-Turbo 人工评判。r4 报告原句当场标废弃，Agent-E 降为背景参照。第三案是报告数字笔误对账：r1 报告把 no_goal/no_reward 写成 6、实为 7（4+3）；'超时 29'去重后实质 600s 击杀 25 格、真超时现象 48 格；r3 的'官方失败 24'勘误为 42——24 只是其中 junit=true 的幻觉子集。三案共性：修正全往对自己不利的方向改——功劳改低、锚点废弃、失分桶变大，而且一手报告原文保留、更正另立权威行。"
**收尾金句**："报告可以出错，改错的方向不能错——三次修正没有一次是往高了改的。"
