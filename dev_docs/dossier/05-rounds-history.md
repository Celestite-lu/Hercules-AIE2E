## 1. 这一页讲什么（3 句）

1. 本档案完整记录 MiniWoB++ 全量 125 任务四轮基准迭代（2026-09-22~24 固化）：官方 last-wins 口径 43.2% → 46.4%（干净口径 47.8%）→ 47.2% → **61.6%**，逐轮给出设定、改动、结果、逐格归因、诚实披露与踩坑。

3. 统计素养是暗线：翻转率 16.8%、扣除机制可归因后纯噪声 12.8%、±10 格（±8%）带宽、480s 预期兑现率仅 12%——任何"为什么涨"的追问都要先过"会不会只是噪声"这一关。

## 3. 每轮详录

### 3.1 r1 — 基准轮 43.2%（54/125）

**设定（完整口径披露，round1-report §1）**
- 任务：browsergym registry 全量 125 任务类，每任务单 seed 单次，seed = sha1(exp_id:miniwob:task_id)。
- agent：Hercules 执行内核（planner→executor 三节点 LangGraph），模型 deepseek-v4-pro（全角色单模型），意图经 Gherkin 中转（Given=带 seed 任务 URL / When=指令原文 / Then=任务完成）。
- 观察：md 属性蒸馏 DOM（文本档，非视觉）。计时：页面 episode 240s（原版 10s，**放宽已披露**）；引擎侧 600s。
- 判分：页面原生 `WOB_RAW_REWARD_GLOBAL > 0`（无 LLM 裁判）；P0 加固后 HUD 奖励显示与 START 重开层已封死。
- 可比性限制四条：模型非 GPT-4、计时放宽、Gherkin 中转、单 seed 单次。
- 复现：`uv run python -m record2gherkin.benchmark.orchestrator --exp-id miniwob-r1 --stage full`（断点续跑，seed 派生确定性）。安全闭环：实验前 YELLOW→P0 加固→实验后 GREEN，五类作弊证据全零。对象 git_rev `a2800a1`。

**结果（三口径）**
- 官方 last-wins **54/125 = 43.2%**；首实例 59/125 = 47.2%（4 no_goal + 3 no_reward 计 0）；零重导航子集 37/60 = 61.7%（有选择偏差，只作诚实性指标）。
- 成本 12.9M token；wall ≈ 336s/格。状态分布：通过 54、页面/引擎超时 29、官方失败 36、no_goal/no_reward 6（后勘误实为 7，见 §4.3 案三）。
- 对照（baselines.md）：公开可比带 A 档（零样本/文本-DOM/GPT-4 级）47-60%——首实例 47.2% 触及带内下沿，官方 43.2% 略低于带；Agent-E 81.6% 当时作冲刺锚点（差 34-38pp，**该锚点后于 r4 更正废弃**，见 §4.3 案二）。

**失败拆桶（analysis-r1-failures §1，71 未过格）**

| 桶 | 格数 | 定义 |
|---|---:|---|
| A 判分瑕疵 | 5 | 页面 raw>0 已到手，被 600s 引擎超时/重试崩溃覆盖（白丢分）：click-collapsible-2-nodelay、click-pie、login-user-popup、multi-layouts、use-colorwheel-2（raw=0.537） |
| B 引擎 600s 杀 | 23 | 进程组被杀且页面最终 raw≤0 |
| C 页面 240s 到点 | 25 | 页钟到期 WOB 回 −1，引擎正常收尾 |
| D 立即判负/答错 | 11 | agent 主动 submit/误点即时 −1 |
| E no_goal | 4 | harness 未拿到目标（3 empty utterance + 1 goal JS 报错） |
| F no_reward | 3 | 全程零 reward 事件（drag-cube、draw-line、resize-textarea） |

对账：报告"超时 29"是 130 行（含 5 个重试行）的 status=timeout 行数，去重后实质 600s 击杀 25 格；真"超时现象"合计 **B+C = 48 格（38.4%）**，最大单一失分来源。

**计时分解（10 个引擎杀格逐格实测）**
- **planner LLM 242s ≈ 4% / 实测工具执行 151s ≈ 3% / 其余 ≈93% 是 executor 逐轮 LLM 延迟**——每轮仅 40-1000 token 的微决策（一次 hover/click/取 DOM）。
- 对照基线（12 个通过格均值）：executor 18.2 轮、planner 3.9 轮、span 158s。**被杀格平均 35-60+ 轮 vs 通过格 18 轮**——差距在轮数不在单轮延迟。最极端 email-inbox-forward 101 轮/span 581s。
- 架构反思（analysis-r1-architecture §0）修正了报告初判：planner 轮次不是延迟源（超时格均值 3.2 轮 vs 通过格 3.7）；真凶是 executor "动作后强制重感知"双倍轮次——超时格均值 51.3 轮（通过格 19.9）、"changed browser state" 链断裂均值 25.1 次（通过格 6.4），每断裂一次强制"停链→重感知→再来一轮"；全语料轮间中位 5s/均值 9.0s/p90 23s（n=2981）；单步 nav 上限 50 轮无时间预算（`core/runner.py:24`）。STATUS 09-22 决策日志将此列为三发现之首。

**三大放大器**
1. **页面终局后空转**：23 次实质击杀中页面早已终局，之后平均空转 **273s**（合计 6280s ≈ 1.75h）；A 桶 5 格反向同理（login-user-popup pass@27s 后空转 573s）。根因：引擎不读页面 done/reward 终态。
2. **重导航复位 240s 页钟**：reload 即重开 WOB episode 计时器——email-inbox-forward 16 次导航把页钟"续"到 **+584s** 才到期（email-inbox/-delete 553/581s），页级预算对该类格完全失效。
3. **helper 60s 双超时级联**：7 格明确记载（ascending-numbers、click-menu、daily-calendar、drag-circle、find-greatest、order-food、use-spinner）——单次调用遇延迟尖峰被掐 → planner 把下一步改写 "timed out, retry" → 重试或重导航清空进度；71 败格中 32 格含此改写。

**重导航是净伤害非洗白**：61/125 格重导航 ≥2 次（最多 15 次），**格内洗白 0 格**，6 格反向自伤（其中 5 格即 A 桶判分瑕疵），1 格直接致败（email-inbox-delete 首实例 raw=1，被 8 次重导航拖到 −1）。93% 重导航走同 tab reload（249/267），prompt 还在主动教"刷新=重开 URL"（browser_nav_agent.py L20/L116）。结论：封死通道不改变任何已得成绩，只把隐藏时间税显式化——接近判分中立。

**9 假设与组合预期（analysis-r1-architecture §1/§3）**：H1 判分修复 +4.0pp（+5 格，43.2→47.2，判分中立）；H2 重导航治理（sessionStorage 单次开局为主 + prompt 撤销刷新教学为辅）；H3 延迟压缩（估计 +3~8pp）；H6 分角色模型路由；H4 Gherkin 模板上下文（+2~5pp）；H7 240→480s 对照（上界 20pp，现实 +4~10pp）；H8 停在首个终局奖励；H9 运维（402 熔断 + per-attempt 日志）。**主推组合（不含 H7）预期 50-56%；保守组合 47.2-48.2%；主推+H7 ablation 口径 54-62%**。HUD 加固移除成功信号→验证步注定空转（multi-layouts 页面通过后 46/64 轮、use-colorwheel-2 56/65 轮）被列为 r2 修复方向。

**披露与坑**
- 完成幻觉：29/36 个 official_failed 格 junit_passed=true——agent 自报成功而页面判负，TERMINATE 无页面 reward 校验。
- 可恢复性矩阵（每格只记一个主杠杆）：保守 22 → 76/125 = 60.8%（A 档带上沿）；上界 49 → 103/125 = 82.4%。杠杆不可加总兑现，此为数学上界。
- 坑：3 格重试行因 LLM 402（余额不足）秒崩；attempt1 日志被 attempt2 覆盖；E/F 桶计数笔误（6 应为 7）。
- 能力盲区定性：拖拽/绘制/选区 14 格（无 drag 工具）、画布几何/视觉 11 格（文本 DOM 天然盲区）、email-inbox 多步记忆 10 格（轮数爆炸 + 重导航清进度）。

### 3.2 r1→r2 — 改进包 C1-C7 + 换 GLM：46.4%（干净 47.8%）

**改动清单（round2-report §2，逐条披露）**
1. **模型更换**：deepseek-v4-pro → GLM（planner=glm-5.3，nav/helper=glm-5.3-flash，coding plan 端点；起因 deepseek 余额尽，STATUS 7.6 行）——**多变量混杂，r1→r2 差异不能全部归因于改进包**（每条归因逐项标注）。
2. C1a 判分中立修复：页面奖励优先于引擎 infra 状态（r1 的 H1 落地）——复审实证零"页面已过被判负"，2 个 timeout 审计格翻正（click-shape raw=1@92s、odd-or-even raw=1@62s）、4 格 junit 不再否决页面。
3. C2 终局信号：中性 `EPISODE ENDED` cue——零提前放弃（300 处 cue 全部晚于终局）；但引擎不停车原样保留（40 超时格 zombie 中位 339s），cue 未接入 terminate 判据。
4. C3 单次开局（sessionStorage）：**多导航格 61 → 16**；16 个 nav≥2 败格无一靠重导航翻正——重导航不再产生分数，只产生墙钟。
5. C4 延迟包：markers_only 重感知/步级预算/prompt 修订——未抗住 GLM-flash 肥尾（见下）。
6. C6 extra_tools：drag 工具启用——61 次调用 0 次成功，0 格因此通过（主因是工具把非 md= 前缀选择器整个包进 `[md='…']` 致 ValueError；且拖拽源根本不在 md 交互元素表），净效果记 −0（净负风险）。
7. C7 模板上下文 + goal 预读非空等待：no_goal 4→1（r1 老 bug 修复）。
8. 运维包：NLTK 语料预装、chromium 回环代理旁路、429 熔断、--max-cells 配速（两段分段执行）。

**r2 三雷（运维层，任务简报口径）**：① key 四键链（GLM 接入的密钥配置链；实测以"key 双 grep 零命中——GLM/DeepSeek 两 key 对 dev_runs 全目录"收口，round2-report §3）；② 系统代理回环（chromium 走系统代理打回环，以上述"回环代理旁路"修复）；③ NLTK 挂死（r1 挂死根因，r2 语料预装根治）。注：round2-report 未出现"C5"编号（C4 直接跳 C6），"四键链"的具体构成**未核实**（一手报告只记结果不记过程），三雷归位以运维条目为准。

**结果**
- 官方 last-wins **58/125 = 46.4%**（r1 +4 格）；**干净 headline（剔除 11 个安全事件格）55/115 = 47.8%**，触及 A 档下沿；**首实例 58/125 = 46.4% 与官方完全相等——零洗白，两口径首次统一**；零重导航子集 55/102 = 53.9%。
- 成本 **9.08M token**（GLM coding plan 额度内）。失败结构：超时 41（最大桶）、官方失败 23、no_goal 1、no_reward 2（合计 67 格，analysis-r2-failures）。
- 结构性迁移：r1 最大桶是"引擎 600s 击杀 + 判分瑕疵"，r2 的 41 个超时格**全部是页面 240s 时钟先杀**（C1a 生效后页面通过不可能再被覆盖）——约束从"引擎限时"移到"页面 240s 时钟 × 单步延迟"。

**W2 安全事件（YELLOW 全案，round2-report §3 + 04 档案）**
- 实验后复审 YELLOW：`persist_findings`（extra_tools 文件工具）在 10 格被调用——9 格静默写诊断笔记、内容良性零判分影响，但成功路径绕过扫描器；按**预登记契约** 10 格全部记无效 → 干净口径 55/115。
- click-shape：沙箱 8 次调用全部文件解析失败零执行（扫描器捕获记无效）；其页面通过真实（raw=1 早于沙箱尝试 91s）。
- 3 格 `javascript:` URI 尝试被 open_url 的 https:// 前缀**偶然**化解——判定为不可依赖，r3 必须补 scheme 白名单。
- 判分本身零作弊：五类应为零指标全零，11 次重试全部维持原判。

**归因与混杂披露（analysis-r2-failures §5）**
- 任务级迁移：r1fail→r2pass 10 格、r1pass→r2fail 6 格 → 官方净 +4。10 个新过格中 3 格是 r1 的 D 桶理解错误（choose-date-easy、click-checkboxes、click-tab-2-medium），C 包无对应杠杆——**指向 GLM 能力**；倒退 6 格多为 r1 靠 deepseek 速度险过的格。模型混杂双向都在，不可分。
- **GLM 肥尾（r2 核心新发现）**：>800 token 的长补全 turn 轮间中位 46.2s/p90 80s（n=3197 executor turn）；**10.3% 的 turn（>500 token）消耗全部 executor 墙钟的 38%**（14426s/37635s）。C4 延迟包被肥尾抵消；r1 的 helper 60s 级联换位成 r2 的 planner 90s 级联——25/41 超时格发生 ≥1 次 planner 90s 超时（draw-circle 10 次），2 格因此秒死（click-shades、drag-shapes-2，零执行判负）。
- 完成幻觉 15/23（65%，绝对数降占比仍高）。

**披露与坑**
- 可恢复性矩阵：保守 21 → 79/125 = 63.2%；上界 53 → 111/125 = 88.8%（数学上界）。
- 480s 预估（r2 版）：上界 16 格 / 保守 6 格（僵尸期仍正确执行的计时敏感格）。
- 坑：reward 事件含跨阶段陈旧数据需按 (task, seed)+run 窗口过滤；drag_and_drop 契约错配浪费 61 次调用各烧 1-2 轮。

### 3.3 r2→r3 — R3-1~6 与 max_tokens no-op 全案：47.2%（官方=clean 首次统一）

**改动清单（round3-report §2 + 任务简报）**
- R3-1 nav 补全上限 768 → **no-op**（全案见下）。
- R3-2 planner 双层 150s → **生效**：超时 41→21 的主要来源（r2 的 25/41 超时格中招 planner 90s 链；r3 全部 21 个超时格 planner 超时 0 次，2 个秒死格复活）。
- R3-3 drag 选择器透传修复 → **生效**：拖拽家族 **0/9 → 3/9**（drag-cube/drag-items/drag-sort-numbers），9/9 选择器解析成功，kill-switch 判据达成。
- R3-4 480s 臂 → **未跑**（另批，spec 已备；round3-report 沿用预估 +6~16 格——后被 analysis-r3 校准下调，见 §4.2）。
- R3-5 安全包全收 → **全生效**：extra_tools 收敛为按需子集（persist/recall 全日志零出现）、scheme 白名单**实拦 4 次**（2× javascript:、2× view-source:，涉事格均未通过）、无效格不进重试池 → 零无效格（r2 是 10+1）。
- R3-6 断言纪律 → 未单独归因，与整体合并。

**max_tokens no-op 全案（本轮最重要的事件）**
- 现象：R3-1 flag 在位、引擎注入链正常（768 配置确认注入），但 GLM 端点**不把 max_tokens 当内容硬上限**——实测 768 配置下单轮产出 **19,349 completion token**；全轮 215 个 turn 补全 >768，分布与 r2 同质。
- 结论修正：超时减半**不能**归因于 R3-1；报告与 manifest 修正为 no-op；超时 41→21 的功劳改记 **R3-2 planner 超时链拆除**。
- 沉淀为教训"**声明在位≠生效**"（配置写入成功 ≠ 行为生效，必须实测验证），r4 若要真上限需换实现（如客户端流式截断）。

**结果**

## 4. 横向专题

### 4.1 噪声与方差（r2↔r3 同模型双轮测得）

- **翻转 21/125 = 16.8%**（r2 败→r3 过 11、r2 过→r3 败 10；pass∩pass 48、fail∩fail 56）。
- 扣除机制可归因 5 格（drag×3 = R3-3、click-scroll-list = R3-2、click-menu-2 = 基建）后，**~12.8% 为纯单 seed 噪声翻转**。
- 按 flip=2p(1−p) 反推：**边缘格（p≈0.5）占全网格约 26%（保守）~34%（含机制混杂口径）**；整体表述为 **±10 格 / ±8% 绝对分**的随机摆动带宽。
- 摆动实例：视觉计数 4 格（count-shape/count-sides/click-shape/visual-addition）r2 过 r3 挂——seed 换图即换难度，方差重灾区；use-slider/use-colorwheel-2 未靠 480s、纯靠运行间速度方差自己过了，是"速度方差可兑现"的直接证据。
- 结论：**单 seed 成绩必须带噪声带陈述**；r3 的"持平"与 r4 的"+14.4 个百分点"都要先对照这条带宽解读（r4 的 +18 格净增已超出 ±10 带，且 17 格有逐格机制证据，所以归因成立）。

### 4.2 240s 边际（480s 预期的提出、兑现与下调）

- r1：H7 假设估计 480s 现实转化 +4~10pp（上界 25 格）。
- r2：精确化预估 **480s 可救上界 16 格 / 保守 6 格**（僵尸期仍正确执行、无工具死端的计时敏感格），边界条件三条：引擎 600s 须同步抬高、对肥尾格与工具死端格无效、超时格墙钟翻倍（+~2.5h）。
- r3（240s 不变下的自然兑现）：r2 上界 16 格实际交付 **2 格**（use-slider、click-menu-2），**兑现率 12%**（保守 6 交付 1，17%）。据此把 r3 清单的 480s 期望外推为 **+1±1、上限 +3**——显著低于 round3-report 沿用的"+6~16"。
- 定性根因：r2→r3 的 R3-2 已把"差时间"的格子变成"差执行质量"的格子（T-A 16→5），纯计时放宽的标的池大幅缩水。
- 状态：480s ablation **截至 r4 冻结仍未跑**（r3 起即"另批/待批准"），是否开跑待用户决定；r3 分析的判断是它仍是低成本正杠杆，但**不再是主要增量来源**。
- 回答"240s 是不是分数注水"：原版 10s → 240s 已是 24× 放宽且全程披露；四轮数据证明约束早已不是页钟而是延迟/覆盖/校验（r2 全部超时格页钟先杀但 480s 兑现率仅 12%）——放宽计时买不来分，只改变失败形态。

### 4.4 教训清单

1. **机制改动受益面按机制算不按家族算**（r4）：plan 按 email+find-greatest 给 A 记账，结果 12 格"不可寻址元素"外溢收益未入预期——预估收益时先问"这个机制触达哪些格"，不是"这个家族有几格"。
2. **声明在位≠生效**（r3）：flag 注入成功 ≠ 端点行为改变；任何配置类改动必须实测行为差异（19,349 token 就是反例），否则归因会挂到不存在的杠杆上。
3. **归因敢往低改**（r3）：超时减半从 R3-1 改记 R3-2；480s 预期从 +6~16 下调到 +1±1——用兑现率（12%）校准预估，而不是保住面子。
4. **延迟治理的目标在轮数不在单轮**（r1→r3 主线）：executor 微决策轮数膨胀是 93% 墙钟的来源；放大器会换位（helper 60s 级联 → planner 90s 级联 → executor 90s 停顿+肥尾），拆掉一个要盯下一个。
5. **判分中立修复先行**（r1→r2）：页面奖励优先于进程超时这类"把口径执行对"的修复零争议、先行落地，能力增强与口径变更分开归因、分开陈述。
6. **多 seed 治"测量"不治"能力"**（r3 分析）：majority-of-3 限边缘 21 格是归因稳定化工具（±10→±3，3.5h 墙钟 / 4.3M token）；best-of-3 已拒绝——+4~7 格是口径红利（等效"每格三次机会"），headline 掺水。
7. **单 seed 成绩永远带噪声带陈述**：16.8% 翻转率下，任何小于 ±10 格的轮间差异都不能直接当机制功劳。

### 4.5 r5 方向（四条，round4-report §4）与"不跑新实验刷分"原则

1. 剩余 48 格结构分析（官方失败 ~39：完成幻觉存量 + 能力失败；超时 9；其他）。
2. 多 seed 口径决策（待用户）：majority-of-3 降噪 vs best-of-3（已拒绝，口径掺水）。
3. E1 信标 seed 值校验（一行改动）；视觉/画布家族维持射程外。
4. "不可寻址元素"的更完整覆盖审计（A 的外溢提示还有存量）。

纪律：STATUS 已于 2026-09-24 冻结 61.6%、转入面试材料阶段；r5 方向全部是分析、一行修复与测量口径决策，**不以跑新实验刷分为目标**（任务简报口径，与 r4 报告"数据指向"的克制取向一致：归因已完成、超出噪声带的结论已锁定，再跑只会花 token 买方差）。
