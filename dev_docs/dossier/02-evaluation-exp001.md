# 02 — 评测框架与变异实验（面试复习版）

## 1. 这一页讲什么 + 本档案复习法

这一页回答「简历上变异实验的硬数字是怎么产出来的」：自建 MiniShop demo + 5 类参数化 UI 变异 + 60 格矩阵（6 流程 × 5 变异 × 2 方法），对比「录制→蒸馏→语义执行」与「selector 式 Playwright 基线」的变异存活率（页面被改之后用例还能不能跑过）、首轮通过率与 token 成本。主指标 1.00 vs 0.667，M3 标识符随机化 6/6 vs 0/6，M4 文案改写 5/6 单列。全部设计决策、执行器双 provider 工程（DeepSeek/GLM）、pilot 三轮迭代与环境坑都在这一页；结论边界同样重要——单 demo、单模型、6 格样本不给概率点估计，这些限定词是口径的一部分，不是附注。

复习法：
1. 先背第 5 节必背数字——每个数字都配了白话含义和被问场景。本页全部数字做过逐行复算验证，放心引用，但不要现场扩展出新数字。
2. 第 3 节 15 张决策卡按「面试官问法」过一遍，两张必背卡是「M4 为什么不算主指标」「基线非稻草人」。
3. 第 4 节坑卡当故事讲：先现象、再根因、最后一句教训，别一上来就说答案。
4. 术语口径与简历通俗版对齐：selector（定位元素的代码钩子）、selector 腐烂（前端一改版定位符就失效）、token（大模型计费单位）、seed（随机种子，固定它就能复现同样的页面）。

## 2. 60 秒主线

被问「你的实验怎么设计的」，完整口头回答：

「我搭了一套变异评测实验，回答一个问题：页面改版之后，『录制→蒸馏→语义执行』的工具还能不能用，传统 selector 式自动化会怎么死。四步。第一步，自建一个 demo 商城——单 HTML 文档的 SPA（整个应用在一个页面里，靠 URL # 号后面的部分切换商品列表和下单表单两个视图），本地起服务，无外网依赖，页面完全可控。第二步，定 5 类参数化变异：M0 对照不改；M1 调换表单字段顺序；M2 加卡片横幅改布局；M3 把全部 id/class/testid 按 seed 换成随机哈希；M4 改写按钮文案。变异是渲染参数不是事后改 DOM，同 seed 页面逐字节可复现。第三步，6 条流程 × 5 变异 × 2 方法 = 60 格矩阵，对比我们的语义执行和属性 selector 式 Playwright 基线（只认 id/testid/class，模拟录制器自动生成脚本的经典维护形态）；正式跑之前有 3 格 pilot 试跑吸收环境问题，预算护栏 39 ≤ 40 次硬拦截。第四步，看三个数：变异存活率、首轮通过率、token 成本。结果：主指标——三类结构性变异的存活率均值——1.00 对 0.667，差距全部来自 M3 标识符随机化的 6/6 对 0/6；M0 到 M2 两边全 6/6 打平；M4 文案改写 5/6 对 6/6，概率性变异单列不进主指标。30 次真实执行共 4,109,386 token，均值 136,980。结论边界我主动给：单 demo、6 流程、单模型，6 格样本不给概率点估计。」

## 3. 决策速答卡（15 张）

### 卡 1：实验目标与失败数据纪律
- **面试官会怎么问**：「实验想证明什么？怎么保证数据可信？」
- **30-60 秒回答**：实验只回答三个可量化的数——首轮通过率、变异存活率、token 成本；不设定性评价，不设「演示好看」类目标。核心纪律是「失败也是数据」：每格只跑一次，超时、结果文件缺失、断言失败全部进分母按 0 计，并单列失败清单（每格 run_id 加摘要、240 字符内）。重试只允许基础设施失败（超时、没产物、服务崩），用例失败绝不重跑——防止「重跑到好看为止」。agent 本身有非确定性，我不靠重跑抹平，靠可复现背书：seed 和全部参数记进实验清单文件（manifest），同格重跑页面逐字节一致。
- **追问预案**：「为什么不跑多次做统计显著性？」→ 样本和预算定的就是少而全归因，显著性检验明确划在范围外；机制级差距（6/6 对 0/6）不靠显著性也成立。「同格已有两行结果听谁的？」→ 最后一行胜——那是基础设施重试替代旧行的语义；某格没有结果行按 0 计并列缺失，半途而废的 sweep 抬不高比率。

### 卡 2：为什么自建 MiniShop demo
- **面试官会怎么问**：「为什么不找个真实网站测？」
- **30-60 秒回答**：三个理由——变异要完全可控、实验要可重复、不能依赖外网。形态是单 HTML 文档的 SPA：整个应用一页、hash 路由切两个视图（商品列表和下单表单），约 60 行 Python 标准库 HTTP 服务承载，无后端状态。单文档是硬约束：录制器跨文档导航会断流（录制器已知边界），SPA + hash 路由是 6 条流程各在一次会话内录完的唯一形态；蒸馏产物里会出现「直接打开 #/order」这样的导航，hash 直达必须能落地。多页站、前端框架、真实外网站都被否掉了。
- **追问预案**：「demo 里有什么？」→ 三个商品：无线耳机 Pro ¥299（数码）、桌面台灯 ¥129（家居）、陶瓷马克杯 ¥39（家居），卡片带三个一模一样的「加入清单」按钮——同名按钮正是 F2 的考察点。「页面行为是确定性的吗？」→ 全部客户端行为同步 DOM 更新：搜索按名称子串过滤、筛选按类别加价格、加清单计数加一、数量限幅 1 到 99、提交不做必填校验任何提交都成功——避免半失败状态引入非确定性。

### 卡 3：变异的实现——参数化渲染，不是改 DOM
- **面试官会怎么问**：「变异是运行时注入脚本改 DOM 吗？怎么保证可重复？」
- **30-60 秒回答**：不是。变异是渲染参数——一个二元组（变异类型，seed），变换作用在结构层的元素注册表上，序列化成 HTML 之前就完成。注册表是单一事实来源：每个可交互、可断言的元素一条记录，M3 的变换范围、完整性单测、基线的预期 selector 全部从它生成，不手抄页面源码，两边不漂移。渲染是纯函数：不读时钟、不读环境，需要随机的地方一律用 seed 做哈希，同参数两次渲染逐字节相同——所以可以离线单测，不用起浏览器。
- **追问预案**：「那页面自己的 JS 怎么办？M3 把 id 全换了，页面会不会自己坏？」→ 这是评审时专门拦下来的问题：如果 JS 里硬编码元素 id，M3 页面的搜索、筛选会静默失效，失败会被误记成「引擎扛不住变异」，主指标整体被污染。所以内联 JS 与 HTML 同源生成——JS 用从变异后注册表生成的映射表找元素；有专门的单元测试机械断言「JS 引用的每个 id 都存在于产物 DOM」，外加真浏览器用例（固定 seed 42）证明 M3 下搜索/筛选/下单行为完好。「为什么不做预生成的多版本页面？」→ M3「每次加载都不同」的语义要用 N 份静态文件模拟，源码一漂移就失控；注入式改 DOM 又和执行环境时序耦合、没法单测。「M2 的横幅会不会干扰断言？」→ 横幅是固定文案（「全场满 99 元包邮，次日达限时 8 折」），与全部断言文本不冲突，M2 不能借横幅制造假差异。

### 卡 4：五类变异 M0-M4
- **面试官会怎么问**：「五种变异分别改什么？为什么是这五种？」
- **30-60 秒回答**：M0 对照，按注册表原样渲染。M1 字段调换：下单表单 7 个字段组顺序反转（提交固定最后），列表页搜索组和筛选组互换——模拟「产品迭代把表单字段挪了」。M2 布局嵌套：每个字段组包一层卡片（共 9 张：列表页 2 + 表单 7）、加弹性布局容器 2 处、页面加横幅——模拟「改版加卡片和横幅」。M3 标识符随机化（主指标）：全部元素的 id/class/testid 按 seed 换成随机哈希，aria-label、label 关联、可见文本一律不动（label 的 for 指向同步换成新 id）——模拟「构建管线给类名加哈希、前端框架动态 id」，真实世界 selector 腐烂的头号来源。M4 文案改写（副指标单列）：7 个键（搜索/筛选/提交/去下单按钮 + 3 个商品加入按钮）各两个候选文案，按 seed 概率选一个，按钮文本和 aria-label 同时改；数量加减符号、返回按钮、全部断言文案不动——模拟「运营改文案」。五类与总计划定死的集合一致，不增不减。
- **追问预案**：「为什么不多加几类？」→ 预算和周期约束；复合变异（比如 M1 加 M3）明确划在范围外。「所有变异共同保证什么？」→ 四个不变量：可访问名文本（除 M4 按规则改按钮名）、断言文案、下拉选项文本、页面标题不变——这是蒸馏产物 feature 里的字面值不被变异破坏、事实回查不受影响的前提，也是断言只引用固定文案的原因。「M4 的『概率性』怎么体现？」→ 同 seed 确定、异 seed 组合不同，单测用 8 个 seed 验证至少出现 2 种组合。

### 卡 5：M4 为什么不算主指标（必背）
- **面试官会怎么问**：「M4 为什么单列？是不是怕它拉低主指标？」
- **30-60 秒回答**：性质不同。M1/M2/M3 是结构性变异，改的是页面结构和标识符，考的是定位和感知的机制，结果由机制决定；M4 是概率性变异——我们这边赌大模型把新文案映射回语义，映射失败还可能静默；基线那边属性 selector 天然不看文案，等于天然免疫。两边的运气成分完全不对称，而且 6 个格子根本给不出概率点估计，并进主指标会污染「机制性存活」的含义。所以如实单列：5/6 对 6/6——注意这对我们不利（基线满分），保留它恰恰是口径诚实。
- **追问预案**：「那个唯一失败格是怎么回事？」→ generated 侧 F5×M4：F5 有 16 条 Then 断言绑定录制时的原文案，M4 改写了导航和按钮文案后，断言找「去下单」发现页面是「马上下单」、找「搜索」发现是「查一下」，断言如实变红——但操作步骤全部语义映射成功（导航回了列表页、状态文案都在）。归因器用「断言不匹配」规则签名定位根因、无大模型时诚实降级，报告的根因证据直指文案改写，替代假设里有「用例过时」；这次真实失败后来还拿去验证了归因器。这是「语义自愈的概率性边界」的量化，不是缺陷。

### 卡 6：基线非稻草人（必背）
- **面试官会怎么问**：「主指标 1.00 对 0.667，基线是不是故意做弱的？」
- **30-60 秒回答**：不是，三个证据。第一，口径：基线是属性 selector 式 Playwright 脚本——按 id、data-testid、class 的优先级定位，模拟录制器自动生成脚本（codegen）产物的经典维护形态；id/class/testid 是工程里最常用的持久定位锚。绝对 XPath 没被采用——它比属性 selector 更脆，M1/M2 布局一动就挂，用它才是更弱的稻草人，选属性 selector 是对基线更有利的形态。第二，结果：M1、M2 下基线照样 6/6、和我们打平，报告如实并列——差距全部来自 M3，而 M3 正是 selector 腐烂痛点本身。第三，预期是预注册的：实验开始前就在计划文档里写明「M1/M2 基线预期存活、M3 基线预期全灭、M4 各凭运气」，防的就是「数据不好看就改口径」。
- **追问预案**：「为什么不用 get_by_role 语义基线或自愈库？」→ 那会把对比变成「我们的语义方案 vs 另一种语义方案」，偏离 selector 腐烂这个立论点；承认没比，是后续项。「基线的 selector 从哪来？」→ 和 demo 页面同源：从 M0 渲染产物的注册表生成，不手抄源码；M0 下每个元素都有 id（元素名下划线换连字符），所以实际就是 #id 定位。「基线怎么记失败？」→ 断言失败或 selector 失配就抛错、记为失败数据：异常摘要取首行、限 500 字符进失败信息；它的成本和 token 字段恒为空——不经引擎、无大模型、无 JUnit。「千万别踩什么坑？」→ 不能说「基线被我打败三项」——M0-M2 是平局，说错直接坐实稻草人指控。

### 卡 7：六条流程怎么选
- **面试官会怎么问**：「6 条流程怎么定的？」
- **30-60 秒回答**：F1 搜索、F2 加清单（三个同名按钮）、F3 下单表单（hash 导航 + checkbox）、F4 筛选、F5 视图往返、F6 数量下单，录制事件数 3/3/11/4/5/8，覆盖输入、点击、下拉、checkbox、hash 导航、计数断言全部交互形态。两条约束：全部用无密码字段，绕开测试数据注入链路；断言只引用固定文案（比如「共 3 件商品」「下单成功，感谢您的购买！」「订单号：D20260920-001」），不和 M4 改写表冲突——同一套文案和数据常量被渲染器、页面 JS、录制脚本、基线四方引用，杜绝口径漂移。F3 实际 11 个事件超出「每条 4-8 个」的设计——hash 导航两次、checkbox 点击加输入、提交时点击和提交双事件，录制器忠实记录、不规避；其中提交的点击+提交双事件被蒸馏器确定性去重（保点击、弃提交，Then 断言存活），checkbox 的双事件则原样保留进 feature，作为实验观察点。
- **追问预案**：「三个同名按钮怎么定位？」→ 蒸馏产物用「(occurrence N)」语法（第 N 个同名元素），这个语法执行侧从未验证过，pilot 里专门安排 F2 验证（卡 12）。「录制有什么工程参数？」→ 回放步间停顿 450 毫秒、等 300 毫秒延迟快照、快照等待 900 毫秒——回放过快会把多个动作压进最后一个事件的 8 条断言上限，实测 F3 的「下单成功」会被挤掉；真人手速天然满足。「F5 断言为什么偏多？」→ 16 条 Then 断言：视图切换最多带出 8 条新文本（录制器快照窗口），所以把列表状态文案设计在 DOM 前部让断言落进窗口。「蒸馏环节有大模型吗？」→ 零大模型纯模板；守卫链：恰好一个 Feature 一个 Scenario、可被解析、禁含测试数据占位与脱敏标记、禁用大模型润色（违反直接报错）。「这些测试在新克隆的环境能跑吗？」→ 全部离线，浏览器组只打本机回环；录制产物缺失时管线那 12 例整组 skip 并打印重建命令，不会掉坑。

### 卡 8：隔离与执行编排
- **面试官会怎么问**：「60 格怎么跑的？格与格怎么保证不串？」
- **30-60 秒回答**：每格一次独立子进程跑引擎，编排、超时、杀进程都在外层。进程内连跑被明确禁止——上游有四个实证：会话记忆单例会串数据、配置单例重置丢态、输出目录用 import 时刻的时间戳做别名、浏览器管理器关闭是异步的。每个 run 还有自己的独立项目根目录——这是唯一有效的隔离手段，因为上游的输出路径参数实际不影响结果文件落盘位置（坑 6）。指标不抠引擎日志，直接解析它产出的 JUnit XML（测试结果通用格式）：没有 failure/error 子元素就是通过；token 按上游同一套键规则求和；成本缺失记 None、禁止记 0。
- **追问预案**：「为什么不解析引擎日志或往引擎里挂钩子？」→ 日志格式不稳，挂钩子侵入上游。「超时怎么杀？」→ 默认 900 秒，进程组级强杀，浏览器子进程一起带走；正常退出但产物缺失、或产物解析失败，一律记失败绝不静默当通过。「格间页面状态怎么切？」→ 本地 demo 服务进程由 sweep 启停，每格执行前先发控制请求设变异和 seed、再探活（15 秒超时）确认生效——防状态漂移污染下一格；端口 8461 是实验参数，被占硬报错绝不自动换（录制产物把 URL 烘进了 feature）。「失败了怎么诊断？」→ 超时和没产物两类失败把子进程 stdout 最后 4000 字符附进失败摘要，归因器直接消费。「manifest 记什么？」→ 实验编号、阶段、代码版本（只读 .git 文件解析，从不执行 git 命令）、模型名、接口地址、端口、超时、预算、每格 seed——不含 key 也不含 key 前缀。

### 卡 9：key 安全与配置注入
- **面试官会怎么问**：「大模型的 key 怎么管理？会不会泄漏？」
- **30-60 秒回答**：三条防线。第一，key 只经子进程环境变量注入，不进命令行参数（ps 能看到 argv），不进 manifest；空 key 直接拒绝注入。第二，子进程 stdout 和 stderr 合并捕获后先脱敏再落盘——替换 key 全值和它的 8 字符前缀、后缀碎片（太短的 key 不切碎片，防止日志被打成筛子）。第三，收口验收对四个输出目录做实值加前后缀碎片的双重 grep，零命中。key 从仓库根的密钥文件读取，配置只注四个 LLM 环境变量加少量运维键——legacy 直连路径就认这四个，不需要 OPENAI_API_KEY。
- **追问预案**：「运维键有哪几个？」→ 子进程环境一共八个键：四个 LLM 键（模型名、接口地址、接口类型恒 openai、key）加四个运维键，每个运维键都对应一个真实踩过的坑——关遥测（上游 import 即初始化 Sentry 会外发，坑 7）、关 uBlock 扩展（启动联网下载会超时，坑 1）、headless、回环代理旁路（坑 5）。「provider 测试会不会读到我的真实 key？」→ 不会，测试用自带的临时 key 文件，绝不读真实文件；环境变量断言还锁死了模型名和 uBlock 关闭这两个值。

### 卡 10：双 provider——DeepSeek 到 GLM
- **面试官会怎么问**：「实验用的哪个模型？后来为什么换？」
- **30-60 秒回答**：exp001 全程 deepseek-v4-pro。之后 DeepSeek 余额耗尽，从 r2 起实验整体切 GLM（glm-5.3-flash，coding plan）。我没有硬编码换模型，而是给执行器长了一个 provider 开关：每个 provider 声明名字、key 文件、模型、接口地址，默认 deepseek 的行为逐字节不变——「现状口径」和「新 provider」可以干净对比。GLM 的 key 文件是键值对格式（三行），解析器兼容旧的单行格式；文件里就算写了 MODEL、BASE_URL 行，运行时也不读——模型和接口地址恒取代码常量，改模型必须改代码，防止 key 文件内容漂移偷偷改变实验口径。
- **追问预案**：「为什么有的场景还要注 OPENAI_API_KEY？」→ benchmark 线把角色路由改成配置文件路径之后，文件加载成功就屏蔽环境变量方案，而文件省略 key 时规划器是裸的 ChatOpenAI 构造——它只认显式参数或 OPENAI_API_KEY 环境变量，不读我们的模型 key 变量。所以那条链必须恰好注四个键，单测断言多一个都不行。这是「声明在位不等于生效」的环境变量按键生效问题，和 evaluation 的四键是两套消费链。

### 卡 11：seed 与可复现
- **面试官会怎么问**：「怎么保证实验可复现？」
- **30-60 秒回答**：seed 不是随机取的，是从格子坐标派生——实验编号、方法、流程、变异四个字段做哈希。三条性质自动成立：同格重跑页面逐字节相同；同一实验内任意两格 seed 互异（M3「动态 id」的语义天然成立）；实验编号进哈希，pilot 三轮同格 seed 实测全不同，每轮实验天然隔离。初稿设计有个循环引用——seed 由 run_id 算，run_id 里又内嵌 seed——按字面根本写不出代码，评审时被抓出来改成从格坐标派生。manifest 记录全部参数，可复现即可信。
- **追问预案**：「agent 的非确定性怎么办？」→ 不重跑择优，靠 seed 和参数全记录背书（卡 1）。

### 卡 12：pilot 先行
- **面试官会怎么问**：「直接跑 60 格不行吗？为什么先 pilot？」
- **30-60 秒回答**：pilot 的存在意义是吸收执行侧全部未知，只花 4 次预算。3 个格子是特意选的：F3 配对照和 M3——验证 hash URL 直达、checkbox 双事件、M3 页面自身 JS；F2 配对照——验证「(occurrence N)」同名按钮语法，它若失效会在 5 个变异格系统性假失败，而那时预算已锁死没有缓冲。事实证明它兑现了设计目的：pilot001 全灭暴露 uBlock 下载问题，pilot002 暴露模型名 400 和结果文件名污染，三个修复落码后 pilot003 三格全过——F3×M0 花 423,880 token、285.66 秒，F3×M3 花 349,797、383.49 秒，F2×M0 花 62,903、59.76 秒。pilot 暴露的边界回写进 spec 之后，才允许跑全量。
- **追问预案**：「pilot 数据进正式表吗？」→ 不进；首轮通过率口径见卡 15。

### 卡 13：预算护栏 39 ≤ 40
- **面试官会怎么问**：「实验怎么控成本？」
- **30-60 秒回答**：预算是硬约束，护栏落在代码和单测里：pilot 4 次 + 全量 30 次 + 基础设施重试上限 5 次 = 39，红线 40；计划期断言一次，运行期每格开跑前再拦一次。单价按上游实测（46,945 token 折 $0.129）估到 $0.13/次，合计上限 $5.07，低于 $10 预算红线。实际执行：33 次成功（全量 30 + pilot 通过轮 3），pilot 前两轮 8 次失败全是零 token 的基础设施失败，没挤占全量配额。重试只限超时、没产物、服务崩溃三类，用例失败绝不重跑。
- **追问预案**：「最后实际花了多少？」→ 30 次真实执行共 4,109,386 token，均值 136,980；复杂表单流程单次可达 42 万（锚定 pilot003 的 F3×M0 = 423,880），简单流程约 7.3 万。

### 卡 14：成本口径——防双计与 cost_unavailable
- **面试官会怎么问**：「token 怎么统计的？为什么不说美元？」
- **30-60 秒回答**：token 和上游引擎同一套规则：只取「含缓存的用量」前缀、以总 token 结尾的键求和——因为结果展平后同时存在含缓存和不含缓存两组键，字面全取会虚高一倍，这是评审时抓出来的必修项。美元如实报 cost_unavailable：模型调用库的计价表里没有 deepseek-v4-pro，对无价目型号它回传显式 0.0 而不是缺键，我们「缺失记 None 禁记 0」的解析层防线拦不住这种情况——0 美元是计价缺失不是免费。所以报告以 token 为主计量，注明前缀缓存会显著折扣实际费用，不虚构美元数。
- **追问预案**：「指标防线有什么一般性教训？」→ 要分两层：解析层管缺失，解释层管「拿到了但不可信」的值。

### 卡 15：FirstPass 口径公允
- **面试官会怎么问**：「首轮通过率 100% 有没有水分？pilot 跑过的格子还算首次吗？」
- **30-60 秒回答**：口径以正式全量的首跑为准。全量里 F3×M0 确实不是字面上的「第一次执行」——pilot 跑过同一格，但 pilot 用独立实验目录、feature 文件零修改、数据不入正式表，实质公允；这个口径在报告里写明了。
- **追问预案**：「蒸馏产物怎么把关？」→ 见卡 7 追问的守卫链：恰好一 Feature 一 Scenario、可解析、禁测试数据占位、禁大模型润色。

## 4. 踩坑故事卡（13 张）

前三张和系统代理一张是 exp001 本体的环境坑，讲的时候按「现象→根因→修复→教训」走。标注了「05/07 档案讲更顺」的三张发生在 benchmark 线、不在 exp001 本体，本页收录是因为它们共享同一套执行栈。

### 坑 1：uBlock 扩展下载卡死，浏览器初始化全灭（pilot001）
- **故事**：pilot001 全部 4 次执行 8-16 秒即死、状态 no_junit（进程正常退出但结果文件缺失）。逐行看日志：每次都在从 GitHub 下载 uBlock 广告拦截扩展的压缩包（1.61.0 版），然后连接超时。根因：上游引擎默认启用 uBlock，浏览器启动时要联网下载扩展包，本机直连 GitHub 大流量不稳，下载超时直接打断浏览器初始化。修复：子进程环境变量固定关闭 uBlock——demo 站无广告，禁用无副作用；此后成为所有执行链路的标准配置（后来 r2 安全审查还把它列入外呼面收敛：harness 侧外联只剩模型端点加本机回环）。
- **教训**：复用上游引擎时，它默认开启的每一个联网副作用（遥测、扩展下载、更新检查）都要逐一盘点并关停——既是稳定性问题也是安全外呼面问题。

### 坑 2：模型串带前缀被 DeepSeek 400 拒绝（pilot002）
- **故事**：pilot002 浏览器初始化过了，3-6 秒即死，报错原文：端点只支持 deepseek-flash、deepseek-v4-pro，但你传的是带 openai/ 前缀的模型串——spec 初稿按通用调用库的惯例写了前缀名，DeepSeek 端点不认。这个组合在 spec 里本来就是列为「pilot 要验证的点」，pilot 兑现了它的设计目的。修复：模型名定死 deepseek-v4-pro，单测锁值并注明来自 pilot002 复盘。
- **教训**：模型串和接口地址的精确组合必须真调一次才作数——spec 把它列为 pilot 验证点而不是拍死，是对的；反面案例是结论没回写 spec（坑 8）。

### 坑 3：蒸馏标题污染结果文件名，`//` 被当目录分隔符（pilot002）
- **故事**：pilot002 进程收尾抛「文件不存在」，路径里出现两个连续斜杠。来源：默认标题是「Recorded flow on http://127.0.0.1:8461」，上游拿页面标题生成结果文件名，标题里的 `://` 清洗后残留 `//`，被文件系统当嵌套目录。这是阶段一源码分析预告过的缺陷类别，在 pilot002 以硬失败形态坐实。修复：蒸馏器给标题加文件名安全清洗——只保留字母数字下划线、中文、空格、连字符，其余连续段折叠为单个下划线，清洗后为空回退默认标题；修复同时落回蒸馏器模块并带回归测试。
- **教训**：自由文本（页面标题）进文件名的每一处都要过同一套安全清洗；pilot 的价值正是让这类缺陷在 3 格小规模暴露，而不是全量 30 格开花。

### 坑 4：pilot 两轮 8 连败，报告概括句不精确
- **故事**：pilot001 加 pilot002 共 8 次执行全部失败、零 token 成本。实验报告初稿概括为「前两轮 8 次失败都发生在浏览器初始化」——原始日志显示只有第一轮是（uBlock 下载超时）；第二轮 uBlock 已禁用、浏览器初始化通过，死在首次大模型调用 400 和结果文件名上。「失败在哪个阶段」是归因问题，概括句也要经得起原始数据对账。三个修复落码后 pilot003 三格全过；预算上 8 次失败零 token，没有挤占全量的 30 次配额。
- **教训**：实验报告的概括句要经得起原始数据对账；「失败在哪个阶段」不能靠记忆写。

### 坑 5：系统代理劫持回环地址——urllib 与 chromium 两层各中一次（完整故事）
- **故事**：第一层 urllib：本机开系统代理时，sweep 对本地 demo 服务的控制和探活请求拿 502——Python 的 urllib 默认读系统代理，而 macOS 系统代理不豁免 127.0.0.1，本机回环请求被转发给代理再被拒。只有 Python 这类调用中招，playwright 的 chromium 走自己的网络栈不受影响。修复：所有回环 HTTP 调用统一用空代理配置显式禁用代理，测试同法。第二层 chromium：系统代理开启时浏览器也跟随系统代理，而代理不转发回环——本地任务页直接加载成 chrome 错误页。这层是 benchmark 线 MiniWoB 场景踩到的（exp001 当期没中招，纯属本地服务恰好在代理开关间隙跑通）。修复分两半：上游引擎加了一个默认关闭的门控，环境变量开启时给 chromium 追加「旁路回环」启动参数——只旁路回环、外网照走系统代理；评测侧子进程环境同步注入这个开关。
- **教训**：同一个「回环被代理劫持」问题在 urllib 和 chromium 两层各要解一次：Python 层显式空代理，chromium 层回环旁路参数；凡对 localhost 发请求的代码，要么显式禁代理要么用 file://，并把假设写进已知问题；上游改动要 flag 门控默认关。

### 坑 6：上游结果文件实际落盘路径与文档口径不符
- **故事**：按文档口径设计「输出路径参数直落结果文件」，离线实测产物其实在项目根下 output 目录的时间戳子目录里——上游用 import 时刻求值的时间戳做 run 隔离，输出路径参数只写入配置项、不影响实际取数。修复：两级定位——先查直连路径，再扫时间戳子目录取最新修改时间的那个；新单测锁定；每 run 独立项目根保持唯一有效隔离；若 pilot 再发现其它落点只需扩这一个函数。
- **教训**：复用上游前先跑一次「契约探测」，把实测行为写进 spec，别按文档想象设计取数路径。

### 坑 7：上游 import 即初始化 Sentry，「全程离线」被遥测打破
- **故事**：跑离线测试/蒸馏时进程退出输出「Sentry 试图发送 2 条待发事件」。根因：上游配置模块在 import 时就初始化 Sentry 并注册退出外发，凡 import 过它的进程都会尝试联网——import 副作用加退出钩子。修复：所有执行链路的标准环境变量恒含「关闭遥测」；蒸馏批处理在 import 上游之前就设好默认值；蒸馏器测试入口同法。
- **教训**：「离线」要按「零网络尝试」验收；import 副作用型依赖必须在测试入口统一关断。

### 坑 8：pilot 结论没回写 spec——文档与代码漂移点
- **故事**：spec 里模型名至今是初稿的「待验证组合」，代码和单测自坑 2 修复后就是 deepseek-v4-pro；实验报告记录的执行模型也是 deepseek-v4-pro。根因：pilot 结论通过代码和测试注释固化了，但「回写 spec 正文」这步被跳过——pilot003 三格通过后火力转向全量，回写被进度挤掉。口径：引用模型配置以代码和实验报告为准；此漂移不影响实验数据正确性（环境变量注入值有单测锁定）。
- **教训**：「pilot 结论回写 spec」这类闭环动作要列入完成的定义，否则一定被挤掉；好在单测把真相锁住了。

### 坑 9：成本全是 0.0 而不是缺键——None 防线没拦住的 cost_unavailable
- **故事**：spec 规定成本缺失记 None 禁记 0；实际 30 行成本字段全是 0.0——但计价表里根本没有这个型号。根因：模型调用库对无价目型号回传显式 0.0（而非缺键），解析层的 None 防线天然不触发；「0 美元」是计价缺失不是免费。处置：报告层定性 cost_unavailable，以 token 为主计量（4,109,386），注明前缀缓存折扣实际费用，不虚构美元。
- **教训**：指标防线分两层——解析层管缺失，解释层管「拿到了但不可信」的值。

### 坑 10：manifest 被末阶段覆盖，看板显示「没跑过」
- **故事**：exp001 的 manifest 显示全程只跑了 24 秒、引擎执行次数为 0——但明明跑了 30 次。根因：全量和基线是两次 sweep 调用、共用同一实验目录；manifest 每阶段收尾重写，最后写的基线阶段（本地 playwright、0 次引擎调用、23.8 秒）覆盖了全量阶段的 manifest。结果文件是追加式的，60 行两方法俱全。处置：读数以 results.jsonl 和它的聚合指标为准；不改代码（收尾期禁重构）。
- **教训**：多阶段共用目录时，产物文件的所有权（阶段级还是实验级）要在 spec 里写死，否则「看板数字」会骗人。

### 坑 11：DeepSeek 402 余额耗尽——重试格秒崩、无熔断烧预算（这条在 05/07 档案讲更顺）
- **故事**：benchmark 第一轮全量中，3 个格的重试行因大模型 402 余额不足秒崩，烧掉基础设施重试预算；其后 DeepSeek 余额彻底耗尽。根因：预付费余额是运维状态不是代码状态，没有熔断时它以「正常失败格」形态消耗重试池。修复：r2 加熔断器（402 裸子串匹配 + 连续熔断）和 1-token 预检；余额尽后 r2 实验整体切 GLM——为此给评测执行器长出 provider 开关（卡 10），默认 deepseek 行为逐字节不变。
- **教训**：付费 API 的余额是实验变量的一部分；先熔断、再预检、最后才烧预算；换 provider 做成开关而不是改常量。

### 坑 12：GLM 通用端点 403——coding 专用端点才认 coding plan 的 key（这条在 05/07 档案讲更顺）
- **故事**：用智谱通用 paas 端点调 coding plan 签发的 key，被拒 403 model_access_denied。根因：coding plan 走独立服务路径，接口地址和 key 是绑定销售的，通用端点不认。修复：GLM provider 的接口地址常量固定为 coding 专用端点（OpenAI 兼容，接口类型恒 openai），预检也走 provider 配置。
- **教训**：换 provider 时端点常量化 + 预检探测，比「先跑一格再报错」便宜得多。

### 坑 13：NLTK 语料下载挂死——进程活着、日志零进展（这条在 05/07 档案讲更顺，排查方法论通用）
- **故事**：3 个格子进程活着、日志零进展，耗到引擎 600 秒超时判负。排查约 5 分钟、先排除再定位：3 格共同点是连一个 agent 轮次都没产出（排除模型问题）；CPU 近零却不退出（排除死循环，像在等什么）；用 py-spy 抓调用栈——主线程停在 NLTK 语料下载的读取里；再用 lsof 看文件描述符——一条对外网络连接挂着。根因：无头环境首次运行触发 NLTK 分词语料自动下载，网络受限（CDN 不通）无限阻塞。修复：r2 起语料预装进环境，一行运维变更。
- **教训**：挂死别猜——py-spy 看栈、lsof 看连接，两个命令把「卡在哪」变成事实；环境依赖的「首次自动下载」在受限网络下全是定时炸弹。
